The connection whose COMMIT crosses the threshold runs the checkpoint itself, and checkpoints again on each later COMMIT until the WAL is reset below 1000 pages. Most commits stay fast; the occasional commit that triggers a checkpoint is much slower.
F84: Automatic checkpoints, sqlite3_wal_checkpoint(), and PRAGMA wal_checkpoint without an argument all run in PASSIVE mode. PASSIVE copies as many frames as it can without waiting for readers or writers, never invokes the busy handler, and may leave the checkpoint unfinished.
F85: FULL waits through the busy handler until no writer is active and every reader is on the latest snapshot, then copies all frames and syncs the database file. RESTART also waits until readers use only the database file, so the next writer restarts the WAL from its beginning. TRUNCATE does what RESTART does and also truncates the -wal file to zero bytes just before a successful return. These modes are reachable only through sqlite3_wal_checkpoint_v2() or PRAGMA wal_checkpoint(MODE), and they block new writers while pending.
F86: A checkpoint may run alongside readers but must stop at the first WAL frame past any active reader's end mark. In file-format terms, it may not backfill past read-mark[N] for any WAL_READ_LOCK(N), N>0, held by another connection. The checkpoint records its progress as nBackfill in the wal-index and resumes from there on the next invocation, so one long-running read transaction stalls checkpoint progress.
F87: In normal operation the next writer, not the checkpointer, rewinds the WAL. A writer may reset the WAL when nBackfill equals mxFrame and no connection holds WAL_READ_LOCK(1) through WAL_READ_LOCK(4). The writer performs the reset while it holds WAL_WRITE_LOCK. walRestartHdr() sets mxFrame and nBackfill to 0, resets the read marks, increments salt-1, and stores a new salt-2.
F88: When the last connection to a database closes, it runs a final checkpoint while holding SQLITE_LOCK_EXCLUSIVE and then deletes the -wal and -shm files. The WAL survives if the last process exits without closing cleanly or if SQLITE_FCNTL_PERSIST_WAL is set. SQLITE_DBCONFIG_NO_CKPT_ON_CLOSE, added in 3.16.0 (2017-01-02), disables the close-time checkpoint. The safe way to fold a leftover WAL back into the database is to open and close the database; deleting or separating the -wal file can lose committed transactions or corrupt the database.
F89: With synchronous=NORMAL in WAL mode, ordinary commits do not sync. SQLite syncs the WAL before each checkpoint, the database file after each completed checkpoint, and the WAL header when the file is reused. Running checkpoints in a separate thread or process therefore keeps query threads from blocking on fsync, at the cost of durability across power loss. synchronous=FULL adds a WAL sync after every commit.
F90: sqlite3_wal_autocheckpoint(db, N) and PRAGMA wal_autocheckpoint=N set a per-connection threshold (default 1000, or SQLITE_DEFAULT_WAL_AUTOCHECKPOINT at compile time). N of zero or less disables automatic checkpoints. The setting is a wrapper around sqlite3_wal_hook(), whose callback runs after every commit to the WAL and may call sqlite3_wal_checkpoint_v2() on its own criteria.
F91: Litestream v0.5.x takes over checkpointing for the databases it replicates. It holds a long-running read transaction so no other process can checkpoint and restart the WAL, and it runs its own checkpoints in three tiers: PASSIVE when the WAL reaches min-checkpoint-page-count (default 1000 pages, about 4 MB), PASSIVE every checkpoint-interval (default 1m), and a blocking TRUNCATE only if the WAL stays at or above truncate-page-n (default 121359 pages, about 500 MB) after a passive attempt. The passive-first order dates from v0.5.15. Litestream logs 'passive checkpoint skipped' when SQLITE_BUSY is returned.
F92: SQLite's documented remedy for checkpoint starvation is to leave 'reader gaps' (moments with no open read transaction) and attempt checkpoints during them. Applications with many concurrent readers can instead run manual RESTART or TRUNCATE checkpoints, which wait so the checkpoint runs to completion, at the cost of blocking.
F93: To keep commit latency flat, an application can set wal_autocheckpoint to 0 and run checkpoints from a dedicated thread, process or idle-time job. SQLite documents this as the alternative to commit-time checkpoints. Litestream applies the same pattern by owning all checkpoints for the databases it replicates.
F94: The Rails SQLite3Adapter DEFAULT_PRAGMAS (main branch) set journal_mode=WAL, synchronous=NORMAL and journal_size_limit=67108864 (64 MB), and leave wal_autocheckpoint at SQLite's default. With that limit, a -wal file inflated by a large transaction is cut back to 64 MB at the next commit or WAL reset instead of keeping its high-water size.
F95: Two documented causes of unbounded WAL growth are disabling autocheckpoint without a replacement checkpoint job and keeping read transactions open long enough that at least one reader is always active. The growing WAL wastes disk and slows every read. Litestream warns that long-lived readers also turn a forced TRUNCATE into an extended write outage.
F96: Aggressive manual checkpointing from a separate connection while other connections write is the pattern that exposed the WAL-reset race. Tailscale took 'manual control of the checkpoint process' so it could run fast, consistent backups at its 'own aggressive pace', and coverage describes this as a non-standard use that made a rare race recur.
F97: A single large write transaction grows the WAL regardless of checkpoint settings, because the WAL cannot be reset in the middle of a write transaction. Since 3.11.0 (2016-02-15) each changed page is written to the WAL once, so the WAL is proportional to the transaction; older versions could write a page repeatedly once the transaction outgrew the page cache.
F98: WAL-reset bug sequence: (1) one connection completes a checkpoint, leaving the WAL ready to reset; (2) a second checkpoint starts; (3) meanwhile another connection commits, resets the WAL, and writes new frames at its start; (4) the second checkpoint misses the reset because it acts on a stale mxFrame, and it sets nBackfill to the old frame count; (5) later commits grow the WAL past that count; (6) a later checkpoint treats the new frames as already copied and skips them. Those committed pages never reach the database file, which causes lost writes or corruption.
F99: The WAL-reset bug requires WAL mode and two or more connections open on the same database file, in separate threads or processes, that write or checkpoint at the same instant.
F100: The WAL-reset bug is likely present in SQLite 3.7.0 (2010-07-21) through 3.51.2 (2026-01-09). SQLite developer Dan found and fixed it on 2026-03-03; the fix and shipped in 3.51.3 (2026-03-13) and later releases, with backports in 3.44.6 and 3.50.7.
F101: SQLite 3.52.0 (2026-03-06) was withdrawn and its planned features moved to 3.53.0 (2026-04-09). 3.51.3 (2026-03-13) shipped the WAL-reset fix plus minor fixes, and 3.53.0 also lists the WAL-reset fix.
F102: Tailscale reported 19 SQLite database corruptions over about six months, starting with a corrupted backup flagged in August 2025, limited to control-plane configuration data. SQLite developers traced the race from logs written by the tmstmpvfs VFS shim that Tailscale deployed in production.
F103: SQLite enables an automatic checkpoint by default. It fires when a COMMIT leaves the WAL at 1000 pages or more (about 4 MB at 4 KiB pages). The SQLITE_DEFAULT_WAL_AUTOCHECKPOINT compile-time option changes the default. PRAGMA wal_autocheckpoint=N or sqlite3_wal_autocheckpoint(db, N) changes the threshold for one connection, because the mechanism is a per-connection sqlite3_wal_hook() callback. N <= 0 turns automatic checkpoints off.
F104: The automatic checkpoint runs on the thread whose COMMIT pushed the WAL over the threshold, after that commit completes. It then runs again on each later COMMIT until the WAL resets below the threshold. Most commits stay fast, but each commit that triggers a checkpoint is much slower.
F105: A checkpoint does not shrink the WAL file. After a reset SQLite overwrites the existing WAL from the beginning, because overwriting is faster than appending. PRAGMA journal_size_limit=N (default -1, no limit) truncates a larger WAL file to N bytes each time the WAL resets. A TRUNCATE checkpoint truncates the WAL file to zero bytes.
F106: Every checkpoint takes the exclusive WAL_CKPT_LOCK, so only one checkpoint runs at a time. A checkpoint call that finds another checkpoint running returns SQLITE_BUSY at once and does not call the busy handler. FULL, RESTART, and TRUNCATE also take the exclusive writer lock. As a result, an automatic checkpoint can make an application's own checkpoint fail with SQLITE_BUSY.
F107: FULL, RESTART, and TRUNCATE wait for the writer lock and for readers only if a busy handler is configured (for example with PRAGMA busy_timeout). If the busy handler returns 0, the checkpoint continues as a PASSIVE checkpoint, copies what it can, and returns SQLITE_BUSY.
F108: Checkpoints order their I/O for crash safety. With synchronous=NORMAL or FULL, SQLite fsyncs the WAL before it copies frames into the database file, and it fsyncs the database file before the WAL can be reset. The checkpointer writes pages in ascending page-number order to keep writes sequential, but seeks remain, so a checkpoint is slower than a write transaction.
F109: After a crash, wal-index recovery cannot know how many WAL frames were already copied into the database, so it sets nBackfill to 0. The next checkpoint therefore starts again from the first WAL frame.
F110: Applications that need control over checkpoint timing take it over from SQLite: they disable automatic checkpoints (for example PRAGMA wal_autocheckpoint=0) and run checkpoints themselves, often from a dedicated thread or process. SQLite documents this to keep slow checkpoints and fsyncs off the commit path. Litestream does it to replicate the WAL. Tailscale's control plane takes manual control of checkpoints to make fast, consistent backups.
F111: Timer-based application checkpointers can starve under constant load. In February 2026 Syncthing kept SQLite auto-checkpoint enabled and added a timer-based checkpointer, but the timer might never hit a window without an active reader, and hours-long transactions pinned WAL pages. Syncthing's proposed fixes were to run a checkpoint heuristic in the connection pool when a connection is released, and to take an exclusive lock to truncate a WAL that reaches several gigabytes.
F112: To diagnose a growing WAL, run PRAGMA wal_checkpoint(NOOP) (3.51.0 and later) or a PASSIVE checkpoint, and compare the log and checkpointed columns. If checkpointed stays below log after a PASSIVE checkpoint, a concurrent reader or writer stopped the checkpoint. busy=1 from FULL, RESTART, or TRUNCATE means that checkpoint was blocked. Next, look for long read transactions and pending statements with the sqlite_stmt virtual table.
F113: Checkpoint starvation: a checkpoint can run to completion and let the WAL reset only when no other connection is using the WAL. If overlapping readers keep at least one read transaction open at all times, no checkpoint completes, the WAL grows without bound, and queries slow down. SQLite's mitigations are reader gaps (moments with no readers, used for checkpoints) or RESTART and TRUNCATE checkpoints, which run to completion but wait for readers.
F114: A prepared statement that has not been reset keeps its connection's read transaction open and can starve checkpoints. COMMIT does not end that read transaction; it only downgrades the write transaction to a read transaction. Step each statement to SQLITE_DONE or call sqlite3_reset() or sqlite3_finalize(). In one forum case, a Python cursor.execute() without fetchall() held the read open.
F115: If an application checkpoints between Litestream's checkpoints, for example through SQLite's auto-checkpoint, Litestream detects the overwritten WAL and takes a fresh full snapshot. Litestream v0.3 logged the reason 'wal overwritten by another process' and started a new generation. Litestream therefore recommends PRAGMA wal_autocheckpoint = 0 on high-write servers, plus a busy_timeout, because its checkpoints take short write locks.
F116: Litestream takes over checkpointing. It holds a long-running read transaction so that no other process can checkpoint and restart the WAL. It copies new WAL pages into LTX files (v0.5; v0.3 used a shadow WAL) and calls SQLite checkpoints itself.
F117: On macOS, PRAGMA checkpoint_fullfsync=ON makes checkpoints use F_FULLFSYNC; the default is off. If PRAGMA fullfsync is on, every sync uses F_FULLFSYNC and checkpoint_fullfsync has no effect.
F118: The WAL-reset bug is a data race between checkpoints and a committing writer. SQLite developer Dan found it on 2026-03-03. It is likely present in SQLite 3.7.0 (2010-07-21) through 3.51.2 (2026-01-09). Version 3.51.3 (2026-03-13) and later fix it, and backports exist as 3.44.6 and 3.50.7. It affects only WAL-mode databases with two or more connections on the same file, in separate threads or processes, that write or checkpoint at the same instant.
F119: Tailscale's control plane has used SQLite as its primary database since 2022. It takes manual control of checkpointing so that it can take fast, consistent backups: a full database snapshot to S3 every few minutes. This exposed it to the WAL-reset race: 19 corruption incidents over about six months, starting in August 2025. SQLite developers wrote a VFS shim, tmstmpvfs, funded by Tailscale, that logs checkpoint activity. Logging that Tailscale added later caught the race in production about two months on, without corruption.
F120: According to Techzine, SQLite 3.52.0 (2026-03-06) shipped the WAL-reset fix first. SQLite withdrew 3.52.0; Techzine reports that an unrelated floating-point rounding change made existing indexes report false corruption. The 3.52.0 features moved to 3.53.0 (2026-04-09), whose release notes also list the WAL-reset fix. To get the fix, use 3.51.3 or later (including 3.53.0 and later) or the 3.44.6 and 3.50.7 backports; avoid the withdrawn 3.52.0.

SET H:
H1 (run 1): A checkpoint copies committed WAL frames into the main database file. When several frames hold versions of the same page, only the newest version is written; superseded versions are skipped.
H2 (run 1): A checkpoint runs concurrently with readers but must stop at the first WAL frame past the end mark of any active reader, because copying it would overwrite database pages that reader is still using. The checkpointer records its progress in the wal-index and resumes from that point on the next call, so a read transaction that stays open for hours pins every WAL page written after it started.
H3 (run 1): The WAL is reset, not truncated, by default: once every frame has been checkpointed and synced and no reader is still using the WAL, the next writer rewinds to the start of the file and overwrites old frames. A new salt in the WAL header makes stale frames with the old salt invalid, and the header's checkpoint sequence number increments. The -wal file only shrinks when journal_size_limit is set or a TRUNCATE checkpoint runs.
H4 (run 1): Automatic checkpoints are PASSIVE and run inside the committing connection, in the committing thread, when a COMMIT leaves the WAL at or above wal_autocheckpoint pages. The default is 1000 pages (compile-time SQLITE_DEFAULT_WAL_AUTOCHECKPOINT), roughly 4 MB at the default 4096-byte page size. The setting is per connection; zero or a negative value disables it for that connection only.
H5 (run 1): When the last connection to a WAL-mode database closes, SQLite runs a final checkpoint and then deletes the -wal and -shm files. With auto-checkpoint disabled, nothing else bounds WAL growth.
H6 (run 1): sqlite3_wal_checkpoint_v2() and PRAGMA wal_checkpoint accept five modes. PASSIVE copies as many frames as it can without waiting and never calls the busy handler. FULL waits for the current writer to finish and for all readers to reach the latest snapshot, then copies every frame and syncs the database. RESTART does FULL and then waits until no reader uses the WAL, so the next writer restarts the log from the beginning. TRUNCATE does RESTART and then truncates the -wal file to zero bytes. NOOP, added in SQLite 3.51.0, checkpoints nothing and only reports the frame counts.
H7 (run 1): FULL, RESTART and TRUNCATE take the exclusive writer lock and invoke the busy handler while waiting for the lock and for readers. They block new writers while pending but let new readers proceed unimpeded. If the busy handler gives up, the call completes what it can like PASSIVE and returns SQLITE_BUSY; the pragma reports this as busy=1 in its first column.
H8 (run 1): Every checkpoint call first takes an exclusive checkpoint lock. If another connection or process already holds it, the call returns SQLITE_BUSY at once without invoking the busy handler. Checkpoints are therefore mutually exclusive, and a 1000-page auto-checkpoint from any connection can make an application's own RESTART or TRUNCATE checkpoint fail with SQLITE_BUSY.
H9 (run 1): PRAGMA wal_checkpoint returns one row with three columns: busy (0, or 1 if a FULL, RESTART or TRUNCATE checkpoint was blocked), log (frames in the WAL) and checkpointed (frames moved into the database so far). If the database is not in WAL mode the last two columns are -1 and the pragma is a no-op. After a successful TRUNCATE both counts are 0. Ignoring the busy column hides failed checkpoints, which Syncthing found it had been doing.
H10 (run 1): With PRAGMA synchronous=NORMAL in WAL mode the checkpoint is the only sync point: the WAL is fsynced before each checkpoint, the database file after each completed checkpoint, and the WAL header when the file is reused, while ordinary commits do no fsync. synchronous=FULL adds a WAL fsync after every commit; EXTRA is identical to FULL in WAL mode. Litestream recommends NORMAL for this reason.
H11 (run 1): Checkpoints cost more than write transactions because they fsync and seek, and read performance falls as the WAL grows because readers must search it. Frequent checkpoints favour reads; infrequent ones favour writes. Because the committing thread runs auto-checkpoints, most commits are fast but some stall on the checkpoint; running checkpoints from a dedicated thread, process or service keeps commits from blocking on fsync.
H12 (run 1): Checkpoint starvation: if overlapping read transactions ensure there is always at least one active reader, no checkpoint can run to completion and reset the WAL, and the -wal file grows without bound (PASSIVE auto-checkpoints never force the issue). Mitigations are to create reader gaps, keep read transactions short, or issue RESTART or TRUNCATE checkpoints, which wait for readers but can stall writers.
H13 (run 1): A single prepared SELECT that has been stepped to a row but not stepped to SQLITE_DONE or passed to sqlite3_reset() keeps its read transaction open and alone pins the WAL end mark, so the WAL grows past the 1000-page auto-checkpoint threshold even with one connection. A forum reproducer showed this on SQLite 3.30.0 and 3.38.5; resetting or finishing the statement promptly kept the WAL near 4 MB.
H14 (run 1): A checkpoint cannot reset the WAL in the middle of a write transaction, so one large transaction produces a WAL at least as large as the transaction. VACUUM in WAL mode writes the whole rebuilt database into the WAL, nearly doubling disk use until a checkpoint runs. Since SQLite 3.11.0 (2016-02-15) a transaction's WAL footprint is proportional to its size; earlier versions could write the same page more than once.
H15 (run 1): After VACUUM in WAL mode, run PRAGMA wal_checkpoint(TRUNCATE) to move the rebuilt pages into the database and shrink the -wal file; otherwise the space has only moved from the database to the WAL. journal_size_limit does not limit WAL growth during the VACUUM transaction, only after a checkpoint or reset.
H16 (run 1): PRAGMA journal_size_limit (default -1, no limit) truncates the -wal file down to the limit each time a transaction commits or the WAL resets; 0 always truncates to the minimum. It applies to one database on one connection, so with a connection pool it must be set on the connection that performs the checkpoint. Syncthing saw TRUNCATE shrink the WAL to zero bytes despite journal_size_limit=67108864 because the pragma had been set on a different pooled connection.
H17 (run 1): sqlite3_wal_hook() registers a callback invoked after each WAL-mode commit with the connection, the database name and the current number of WAL pages; the callback may read, write or checkpoint, and a non-SQLITE_OK return propagates to the caller although the commit has already happened. Auto-checkpoint (the C function and the pragma) is built on this hook and overwrites any earlier hook; registering your own hook, or passing NULL, replaces auto-checkpoint. This is the intended way to implement custom checkpoint policy.
H18 (run 1): Passing NULL or an empty string as zDb to sqlite3_wal_checkpoint_v2() checkpoints every attached WAL database; pnLog and pnCkpt are then undefined, SQLITE_BUSY on one database does not stop the others, and SQLITE_BUSY is returned at the end. Naming a non-WAL database returns SQLITE_OK with both counts -1; naming an unknown database returns SQLITE_ERROR.
H19 (run 1): Litestream holds a long-running read transaction between its own checkpoints so no other process can checkpoint and restart the WAL before it has copied the frames. Under heavy write load (tens of thousands of small writes per second) an application auto-checkpoint can still slip in, after which Litestream takes a fresh full snapshot; it therefore recommends PRAGMA wal_autocheckpoint=0 plus PRAGMA busy_timeout=5000 in the application. v0.5.0+ improved checkpoint detection reduces the snapshot fallback.
H20 (run 1): Litestream v0.5.x uses a tiered policy: a PASSIVE checkpoint when the WAL exceeds min-checkpoint-page-count (default 1000 pages, about 4 MB) or every checkpoint-interval (default 1m), and an emergency checkpoint when the WAL exceeds truncate-page-n (default 121359 pages, about 500 MB) that tries PASSIVE first and forces TRUNCATE only if the WAL stays above the threshold (passive-first since v0.5.15). A forced TRUNCATE waits for all readers and writers and takes a boundary snapshot under the write lock, so it can stall writers; truncate-page-n=0 avoids blocking but leaves WAL size unbounded.
H21 (run 1): Syncthing's SQLite backend ran PRAGMA wal_checkpoint(TRUNCATE) every 8 hours with a 64 MiB journal_size_limit while leaving SQLite auto-checkpoints enabled and ignoring the busy column. It hit multi-gigabyte WAL files, diagnosed three causes (hours-long read transactions, near-constant activity leaving no idle window for RESTART or TRUNCATE, and auto-checkpoints colliding with its own checkpointer), and proposed disabling auto-checkpoint, a dedicated checkpointer triggered by WAL size or connection release, and shorter read transactions.
H22 (run 1): Splitting long read work into short read transactions and issuing PRAGMA wal_checkpoint(RESTART) when starvation is detected cut Syncthing's WAL on a 2.5 GB database from about 2.2 GB to about 128 MiB during index resets (Syncthing PR #10027).
H23 (run 1): The WAL-reset bug is a data race between a checkpoint and a write transaction that resets the WAL, when two or more connections (separate threads or processes) write or checkpoint at the same instant. The second checkpoint misses the reset and leaves the wal-index backfill count (nBackfill) wrong, so a later checkpoint skips part of a committed transaction: committed pages are never written to the database while pages that reference them are, producing lost writes and a corrupt file. SQLite says it is likely present from 3.7.0 (2010-07-21) through 3.51.2 (2026-01-09); it is fixed in 3.51.3 (2026-03-13) with backports in 3.44.6 and 3.50.7. 3.52.0 also carried the fix but was withdrawn for an unrelated regression.
H24 (run 1): SQLite describes the WAL-reset race as unlikely in common use and says its developers never reproduced it organically, only with a test hook. Tailscale nevertheless recorded 19 corruption incidents over about six months from August 2025 with a single Go process per shard that checkpoints manually and very aggressively, and Antithesis reproduced it on 3.51.2 in about 15 minutes with a generic workload of concurrent writes and checkpoints; the same workload ran clean on 3.51.3. Tailscale had run four months without incidents as of August 2026.
H25 (run 1): The 3.51.3 fix is a single extra check: the checkpointer confirms, by comparing the WAL salt, that the WAL was not reset since the checkpoint began. Canonical's TLA+ model found the corrupting trace in about 20 states; dqlite is unaffected because it blocks user-initiated checkpoints, disables automatic ones and runs its own checkpoint as a stop-the-world action under the write lock, so a writer and a checkpoint can never overlap.
H26 (run 1): Practical hardening for applications that drive checkpoints themselves: upgrade to SQLite 3.51.3 or later; disable auto-checkpoint on every connection if one component owns checkpointing; always check the busy column or SQLITE_BUSY return and retry; run PRAGMA integrity_check on backups continuously; and treat non-standard, aggressive checkpoint schedules as a risk surface, since that is where the WAL-reset race surfaced in production.
