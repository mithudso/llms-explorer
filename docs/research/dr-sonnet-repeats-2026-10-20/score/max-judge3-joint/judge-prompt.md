SET F:
F1: A checkpoint copies committed WAL frames into the main database file. When several frames hold versions of the same page, only the newest version is written; superseded versions are skipped.
F2: A checkpoint runs concurrently with readers but must stop at the first WAL frame past the end mark of any active reader, because copying it would overwrite database pages that reader is still using. The checkpointer records its progress in the wal-index and resumes from that point on the next call, so a read transaction that stays open for hours pins every WAL page written after it started.
F3: The WAL is reset, not truncated, by default: once every frame has been checkpointed and synced and no reader is still using the WAL, the next writer rewinds to the start of the file and overwrites old frames. A new salt in the WAL header makes stale frames with the old salt invalid, and the header's checkpoint sequence number increments. The -wal file only shrinks when journal_size_limit is set or a TRUNCATE checkpoint runs.
F4: Automatic checkpoints are PASSIVE and run inside the committing connection, in the committing thread, when a COMMIT leaves the WAL at or above wal_autocheckpoint pages. The default is 1000 pages (compile-time SQLITE_DEFAULT_WAL_AUTOCHECKPOINT), roughly 4 MB at the default 4096-byte page size. The setting is per connection; zero or a negative value disables it for that connection only.
F5: When the last connection to a WAL-mode database closes, SQLite runs a final checkpoint and then deletes the -wal and -shm files. With auto-checkpoint disabled, nothing else bounds WAL growth.
F6: sqlite3_wal_checkpoint_v2() and PRAGMA wal_checkpoint accept five modes. PASSIVE copies as many frames as it can without waiting and never calls the busy handler. FULL waits for the current writer to finish and for all readers to reach the latest snapshot, then copies every frame and syncs the database. RESTART does FULL and then waits until no reader uses the WAL, so the next writer restarts the log from the beginning. TRUNCATE does RESTART and then truncates the -wal file to zero bytes. NOOP, added in SQLite 3.51.0, checkpoints nothing and only reports the frame counts.
F7: FULL, RESTART and TRUNCATE take the exclusive writer lock and invoke the busy handler while waiting for the lock and for readers. They block new writers while pending but let new readers proceed unimpeded. If the busy handler gives up, the call completes what it can like PASSIVE and returns SQLITE_BUSY; the pragma reports this as busy=1 in its first column.
F8: Every checkpoint call first takes an exclusive checkpoint lock. If another connection or process already holds it, the call returns SQLITE_BUSY at once without invoking the busy handler. Checkpoints are therefore mutually exclusive, and a 1000-page auto-checkpoint from any connection can make an application's own RESTART or TRUNCATE checkpoint fail with SQLITE_BUSY.
F9: PRAGMA wal_checkpoint returns one row with three columns: busy (0, or 1 if a FULL, RESTART or TRUNCATE checkpoint was blocked), log (frames in the WAL) and checkpointed (frames moved into the database so far). If the database is not in WAL mode the last two columns are -1 and the pragma is a no-op. After a successful TRUNCATE both counts are 0. Ignoring the busy column hides failed checkpoints, which Syncthing found it had been doing.
F10: With PRAGMA synchronous=NORMAL in WAL mode the checkpoint is the only sync point: the WAL is fsynced before each checkpoint, the database file after each completed checkpoint, and the WAL header when the file is reused, while ordinary commits do no fsync. synchronous=FULL adds a WAL fsync after every commit; EXTRA is identical to FULL in WAL mode. Litestream recommends NORMAL for this reason.
F11: Checkpoints cost more than write transactions because they fsync and seek, and read performance falls as the WAL grows because readers must search it. Frequent checkpoints favour reads; infrequent ones favour writes. Because the committing thread runs auto-checkpoints, most commits are fast but some stall on the checkpoint; running checkpoints from a dedicated thread, process or service keeps commits from blocking on fsync.
F12: Checkpoint starvation: if overlapping read transactions ensure there is always at least one active reader, no checkpoint can run to completion and reset the WAL, and the -wal file grows without bound (PASSIVE auto-checkpoints never force the issue). Mitigations are to create reader gaps, keep read transactions short, or issue RESTART or TRUNCATE checkpoints, which wait for readers but can stall writers.
F13: A single prepared SELECT that has been stepped to a row but not stepped to SQLITE_DONE or passed to sqlite3_reset() keeps its read transaction open and alone pins the WAL end mark, so the WAL grows past the 1000-page auto-checkpoint threshold even with one connection. A forum reproducer showed this on SQLite 3.30.0 and 3.38.5; resetting or finishing the statement promptly kept the WAL near 4 MB.
F14: A checkpoint cannot reset the WAL in the middle of a write transaction, so one large transaction produces a WAL at least as large as the transaction. VACUUM in WAL mode writes the whole rebuilt database into the WAL, nearly doubling disk use until a checkpoint runs. Since SQLite 3.11.0 (2016-02-15) a transaction's WAL footprint is proportional to its size; earlier versions could write the same page more than once.
F15: After VACUUM in WAL mode, run PRAGMA wal_checkpoint(TRUNCATE) to move the rebuilt pages into the database and shrink the -wal file; otherwise the space has only moved from the database to the WAL. journal_size_limit does not limit WAL growth during the VACUUM transaction, only after a checkpoint or reset.
F16: PRAGMA journal_size_limit (default -1, no limit) truncates the -wal file down to the limit each time a transaction commits or the WAL resets; 0 always truncates to the minimum. It applies to one database on one connection, so with a connection pool it must be set on the connection that performs the checkpoint. Syncthing saw TRUNCATE shrink the WAL to zero bytes despite journal_size_limit=67108864 because the pragma had been set on a different pooled connection.
F17: sqlite3_wal_hook() registers a callback invoked after each WAL-mode commit with the connection, the database name and the current number of WAL pages; the callback may read, write or checkpoint, and a non-SQLITE_OK return propagates to the caller although the commit has already happened. Auto-checkpoint (the C function and the pragma) is built on this hook and overwrites any earlier hook; registering your own hook, or passing NULL, replaces auto-checkpoint. This is the intended way to implement custom checkpoint policy.
F18: Passing NULL or an empty string as zDb to sqlite3_wal_checkpoint_v2() checkpoints every attached WAL database; pnLog and pnCkpt are then undefined, SQLITE_BUSY on one database does not stop the others, and SQLITE_BUSY is returned at the end. Naming a non-WAL database returns SQLITE_OK with both counts -1; naming an unknown database returns SQLITE_ERROR.
F19: Litestream holds a long-running read transaction between its own checkpoints so no other process can checkpoint and restart the WAL before it has copied the frames. Under heavy write load (tens of thousands of small writes per second) an application auto-checkpoint can still slip in, after which Litestream takes a fresh full snapshot; it therefore recommends PRAGMA wal_autocheckpoint=0 plus PRAGMA busy_timeout=5000 in the application. v0.5.0+ improved checkpoint detection reduces the snapshot fallback.
F20: Litestream v0.5.x uses a tiered policy: a PASSIVE checkpoint when the WAL exceeds min-checkpoint-page-count (default 1000 pages, about 4 MB) or every checkpoint-interval (default 1m), and an emergency checkpoint when the WAL exceeds truncate-page-n (default 121359 pages, about 500 MB) that tries PASSIVE first and forces TRUNCATE only if the WAL stays above the threshold (passive-first since v0.5.15). A forced TRUNCATE waits for all readers and writers and takes a boundary snapshot under the write lock, so it can stall writers; truncate-page-n=0 avoids blocking but leaves WAL size unbounded.
F21: Syncthing's SQLite backend ran PRAGMA wal_checkpoint(TRUNCATE) every 8 hours with a 64 MiB journal_size_limit while leaving SQLite auto-checkpoints enabled and ignoring the busy column. It hit multi-gigabyte WAL files, diagnosed three causes (hours-long read transactions, near-constant activity leaving no idle window for RESTART or TRUNCATE, and auto-checkpoints colliding with its own checkpointer), and proposed disabling auto-checkpoint, a dedicated checkpointer triggered by WAL size or connection release, and shorter read transactions.
F22: Splitting long read work into short read transactions and issuing PRAGMA wal_checkpoint(RESTART) when starvation is detected cut Syncthing's WAL on a 2.5 GB database from about 2.2 GB to about 128 MiB during index resets (Syncthing PR #10027).
F23: The WAL-reset bug is a data race between a checkpoint and a write transaction that resets the WAL, when two or more connections (separate threads or processes) write or checkpoint at the same instant. The second checkpoint misses the reset and leaves the wal-index backfill count (nBackfill) wrong, so a later checkpoint skips part of a committed transaction: committed pages are never written to the database while pages that reference them are, producing lost writes and a corrupt file. SQLite says it is likely present from 3.7.0 (2010-07-21) through 3.51.2 (2026-01-09); it is fixed in 3.51.3 (2026-03-13) with backports in 3.44.6 and 3.50.7. 3.52.0 also carried the fix but was withdrawn for an unrelated regression.
F24: SQLite describes the WAL-reset race as unlikely in common use and says its developers never reproduced it organically, only with a test hook. Tailscale nevertheless recorded 19 corruption incidents over about six months from August 2025 with a single Go process per shard that checkpoints manually and very aggressively, and Antithesis reproduced it on 3.51.2 in about 15 minutes with a generic workload of concurrent writes and checkpoints; the same workload ran clean on 3.51.3. Tailscale had run four months without incidents as of August 2026.
F25: The 3.51.3 fix is a single extra check: the checkpointer confirms, by comparing the WAL salt, that the WAL was not reset since the checkpoint began. Canonical's TLA+ model found the corrupting trace in about 20 states; dqlite is unaffected because it blocks user-initiated checkpoints, disables automatic ones and runs its own checkpoint as a stop-the-world action under the write lock, so a writer and a checkpoint can never overlap.
F26: Practical hardening for applications that drive checkpoints themselves: upgrade to SQLite 3.51.3 or later; disable auto-checkpoint on every connection if one component owns checkpointing; always check the busy column or SQLITE_BUSY return and retry; run PRAGMA integrity_check on backups continuously; and treat non-standard, aggressive checkpoint schedules as a risk surface, since that is where the WAL-reset race surfaced in production.

If many overlapping readers keep at least one reader active at all times, no checkpoint ever completes. SQLite's remedy is reader gaps: times with no readers, when checkpoints are attempted. With many concurrent readers, SQLite also suggests manual RESTART or TRUNCATE checkpoints, which run to completion before returning, at the price that readers might block. A Syncthing maintainer summarized the effect in February 2026: the WAL grows indefinitely until a checkpoint completes, and multiple gigabytes is critical.
H51 (run 2): In the Syncthing thread of 2026-02-06, the maintainer named three causes that keep checkpoints from truncating a growing WAL: transactions open for hours, such as vacuum; no quiet window for a timer-based application checkpointer, because the database is read and written almost constantly while a large folder is processed; and auto-checkpoints left on, so commits run passive checkpoints that block the application's own exclusive checkpointer. The maintainer also floated running the checkpoint heuristic when a connection returns to the pool.
H52 (run 2): A manual PRAGMA wal_checkpoint(RESTART) or sqlite3_wal_checkpoint_v2() can return SQLITE_BUSY in about a microsecond even when every connection has busy_timeout=10000. In a 2021 SQLite forum case (36 connections, about 1000 writes per second), the cause was auto-checkpoints running on other connections. The checkpoint lock is exclusive and the busy handler does not apply to it. Setting PRAGMA wal_autocheckpoint=0 on every connection fixed it.
H53 (run 2): Mixing auto-checkpoints with an external checkpointer makes them collide. Litestream says an application checkpoint can land between Litestream's checkpoints, make Litestream miss a WAL update, and force a fresh full snapshot; it recommends PRAGMA wal_autocheckpoint = 0 for high write load. Syncthing's maintainer reports the same lock conflict from the other side: commit-triggered passive checkpoints block the application's own checkpointer.
H54 (run 2): Litestream v0.5.x runs three checkpoint tiers after each sync and checks the emergency tier first. The page-count tier runs a PASSIVE checkpoint when the WAL exceeds min-checkpoint-page-count, default 1000 pages (about 4 MB). The time tier runs a PASSIVE checkpoint every checkpoint-interval, default 1 minute, if the WAL has at least 1 page. The emergency tier, truncate-page-n, defaults to 121359 pages (about 500 MB). Since v0.5.15 it tries PASSIVE first and forces TRUNCATE only if the WAL stays above the threshold. Setting checkpoint-interval or truncate-page-n to 0 disables that tier. min-checkpoint-page-count cannot be 0.
H55 (run 2): A forced Litestream TRUNCATE inherits RESTART semantics: it waits for active readers and writers, and it blocks writers while it waits. A long-lived reader therefore causes write timeouts and 'database is locked' errors. The log line 'forcing truncate checkpoint' marks a blocking checkpoint. The line 'wal restarted by passive checkpoint, skipping truncate checkpoint' means the passive attempt avoided one. For apps with long-lived readers, Litestream suggests truncate-page-n: 0 plus monitoring of the -wal size, which accepts unbounded WAL growth.
H56 (run 2): The WAL-reset bug can lose committed transactions and corrupt a WAL-mode database. SQLite's WAL page says it is likely present in every release from 3.7.0 (2010-07-21) through 3.51.2 (2026-01-09). SQLite developer Dan found and fixed it on 2026-03-03. The fix ships in 3.51.3 (2026-03-13) and later, with backports in 3.44.6 and 3.50.7.
H57 (run 2): The WAL-reset bug needs a WAL-mode database with two or more connections open in separate threads or processes that write or checkpoint at the same instant. The sequence: a first checkpoint completes fully; a second checkpoint starts; while it starts, another connection commits a transaction that resets the WAL and writes new frames at its beginning; the second checkpoint misses the reset because of a data race and leaves a wal-index header field claiming frames are already checkpointed; later commits grow the WAL past its earlier length; a third checkpoint then skips part of the transaction written after the reset, so those pages never reach the database file.
H58 (run 2): SQLite rates the WAL-reset bug as a data race with tight timing that is unlikely in common use. It says its developers could not reproduce the bug organically and needed a sqlite3_test_control() callback to trigger it, and that it is not an emergency: the occurrence rate in the wild appears no higher than that of SSD malfunctions or cosmic-ray hits. It still advises upgrading to a fixed version.
H59 (run 2): Phil Eaton (2026-08-23) reproduced the bug with about 100 lines of C that use only the public SQLite API: two threads, three connections, explicit PASSIVE checkpoints, and a canary table that records every committed insert. On the 3.51.2 amalgamation it lost a committed transaction, or produced 'database disk image is malformed', within about 3.5 to 4.3 seconds per run. A 3.53.0 build lost nothing in a run of about 16 seconds. SQLite's WAL page was updated on 2026-08-24 to point to this reproducer, which needs no special test hook.
H60 (run 2): In Eaton's trace of the race, the checkpointer reads the wal-index header (mxFrame=360). A writer then runs walRestartHdr (mxFrame=0, salt incremented, nBackfill=0, read marks cleared) and commits 5 new frames. The checkpointer's stale check nBackfill < mxFrame still passes, so it sets nBackfill=360, and the next checkpoint starts at frame 361 and skips frames 1 to 5, which hold live data. A large database with a large mmap_size widens the window because wal.c unmaps the database file inside it. ThreadSanitizer on 3.51.2 flagged the read of nBackfill in walCheckpoint against the atomic store in walRestartHdr.
H61 (run 2): A lost write can occur while PRAGMA integrity_check still returns ok. Eaton's second 3.51.2 run lost one transaction and printed 'permanently lost: 1 transactions' followed by 'integrity_check: ok'. Tailscale's backups detected corruption, and its transaction log showed committed data disappearing during later transactions. Eaton notes that SQLite does not guard against lost writes even after the fix.
H62 (run 2): Tailscale hit the WAL-reset bug in production. Techzine reports nineteen database corruption incidents over about half a year in a control plane where Tailscale triggers checkpoints itself, to take fast and predictable backups, instead of letting SQLite do it. A Tailscale engineer told The Register that taking manual control and running at its own aggressive pace took the team off the well-trodden operational path. Both reports derive from Tailscale's own post-mortem.
H63 (run 2): SQLite withdrew 3.52.0 after Tailscale reported corruption in thirteen databases. Techzine calls that report a false alarm: a change in floating-point rounding made existing indexes look corrupt. Antithesis describes the same episode as a fix that was rolled out, rolled back, and re-verified in 3.51.3. The 3.51.3 release notes (2026-03-13) list the WAL-reset fix plus other minor bug fixes.
H64 (run 2): Antithesis (2026-08-12) caught the bug on 3.51.2 in about 15 minutes of its first run, using a generic workload that only runs writes and checkpoints concurrently and standard assertions such as no lost committed writes and an integrity check. The same workload on 3.51.3 came back clean in the one reported run. Eaton's separate reproducer also passed on fixed 3.53.0 in a run of about 16 seconds. Both clean results are small samples.
H65 (run 2): To see whether checkpoints keep up, compare the log and checkpointed counts that PRAGMA wal_checkpoint returns. PRAGMA wal_checkpoint(NOOP), available from SQLite 3.51.0, reads both counts without copying any frame. A PASSIVE checkpoint can leave frames behind when readers or writers are active, so a gap that persists across PASSIVE runs is consistent with a long-lived reader. Litestream's troubleshooting steps run PRAGMA wal_checkpoint(PASSIVE) for this diagnosis and watch the -wal file size, which is a high-water mark and does not shrink after a normal checkpoint.
H66 (run 2): Do not separate a WAL-mode database from its -wal file. If the .db file is copied or moved without its -wal file, committed transactions can be lost and the database can become corrupt. The only safe way to remove a leftover -wal file is to open the database with a sqlite3_open() interface and close it with sqlite3_close(). Litestream's tips describe the hazard from the other side: if you delete the .db but leave the -wal, SQLite applies the old WAL pages to the new database.
H67 (run 2): A very large write transaction can create a very large WAL. A checkpoint cannot reset the WAL in the middle of a write transaction, so the file can grow until the transaction ends and no reader blocks the checkpoint. Since SQLite 3.11.0 (2016-02-15) the WAL for a single transaction is proportional to the transaction's size; older versions could write the same page into the WAL several times once the transaction outgrew the page cache.
H68 (run 2): The wal-index (-shm file) needs more than one hash table only when the WAL exceeds 4079 frames. The default threshold of 1000 pages rarely reaches that size, so a higher wal_autocheckpoint value lets the shm file grow beyond one hash table once the WAL passes 4079 frames.
H69 (run 2): After a crash, recovery scans the WAL from the start and stops at the first invalid checksum. It sets mxFrame to the last valid commit frame and sets nBackfill to zero, because it cannot know how many frames earlier checkpoints already copied. The wal-index therefore no longer records any earlier checkpoint progress.
H70 (run 3): A checkpoint moves committed transactions from the WAL file back into the main database file. By default SQLite checkpoints automatically after a COMMIT leaves the WAL at 1000 pages or more, and again when the last connection to the database closes. The compile-time option SQLITE_DEFAULT_WAL_AUTOCHECKPOINT changes the 1000-page default.
H71 (run 3): The automatic checkpoint runs on the same thread that issued the COMMIT that pushed the WAL over the threshold, after the commit finishes. Most commits stay fast, and the occasional commit that triggers a checkpoint is slower.
H72 (run 3): In WAL mode with synchronous=NORMAL, the checkpoint is the only operation that issues a sync. SQLite syncs the WAL before each checkpoint, syncs the database file after each completed checkpoint, and syncs the WAL header when it starts reusing the WAL. With synchronous=FULL, each commit also syncs the WAL. WAL with NORMAL stays consistent but can lose the latest commits after a power loss or system crash; commits survive an application crash.
H73 (run 3): All automatic checkpoints are PASSIVE, and so are checkpoints started by sqlite3_wal_checkpoint(). A PASSIVE checkpoint copies as many frames as it can without waiting for readers or writers, never calls the busy handler, and may leave frames uncopied while readers or writers are active.
H74 (run 3): FULL, RESTART and TRUNCATE call the busy handler while they wait. FULL waits until no writer is active and all readers use the newest snapshot, then copies every frame and syncs the database file. RESTART does the same, then waits until all readers read only the database file, so the next writer restarts the WAL from the beginning. TRUNCATE does the same as RESTART, then truncates the WAL file to zero bytes before it returns successfully. While pending, each of the three blocks new writers; the C API and PRAGMA docs say new readers continue.
H75 (run 3): SQLite 3.51.0 (2025-11-04) added PRAGMA wal_checkpoint=NOOP and the SQLITE_CHECKPOINT_NOOP argument to sqlite3_wal_checkpoint_v2(). NOOP checkpoints zero frames. Its only purpose is to read the log-size and checkpointed-frame counts.
H76 (run 3): A checkpoint can run while readers are active. It must stop at the first WAL frame past the end mark of any current reader, because that reader still needs the older database pages. The checkpoint records how far it got in the wal-index and resumes from that point on its next run.
H77 (run 3): After a checkpoint has copied the whole WAL into the database file and no reader still depends on the WAL, the next writer rewinds to the start of the WAL file and overwrites it. This reset is what bounds WAL size. If at least one reader is always active, no checkpoint can finish, the reset never happens, and the WAL file grows without bound.
H78 (run 3): A completed checkpoint does not shrink the -wal file; SQLite starts overwriting the file from the beginning. The file shrinks only if PRAGMA journal_size_limit is set (SQLite then truncates the WAL to that limit when a transaction commits or the WAL resets) or if a TRUNCATE checkpoint succeeds. The default journal_size_limit is -1, which means no limit.
H79 (run 3): When the last connection to a WAL-mode database closes or detaches, SQLite runs one final checkpoint and deletes the WAL file. sqlite3_db_config(SQLITE_DBCONFIG_NO_CKPT_ON_CLOSE) turns off that final checkpoint: a positive value disables it, and zero (the default) enables it.
H80 (run 3): sqlite3_wal_autocheckpoint(db, N) and PRAGMA wal_autocheckpoint = N wrap sqlite3_wal_hook(). Zero or a negative N turns automatic checkpoints off. Registering a different WAL hook turns the automatic checkpoint off, and calling sqlite3_wal_autocheckpoint() replaces any earlier hook.
H81 (run 3): A WAL hook runs after each commit, after the write lock is released, and receives the number of pages now in the WAL. The hook may read, write or checkpoint the database, so an application can implement its own checkpoint policy. An error code returned from the hook propagates to the statement that triggered it, although the commit has already happened.
H82 (run 3): PRAGMA wal_checkpoint returns one row of three integers. Column 1 is 0 normally and 1 when a FULL, RESTART or TRUNCATE checkpoint was blocked from completing, which matches SQLITE_BUSY from sqlite3_wal_checkpoint_v2(). Column 2 is the number of modified pages in the WAL. Column 3 is the number of those pages moved back into the database file. Columns 2 and 3 are -1 when the database is not in WAL mode. After a successful TRUNCATE, the C API reports 0 frames in both output parameters.
H83 (run 3): Read cost grows with WAL size: every reader must check the WAL for the page it wants. The wal-index speeds up that lookup but read performance still falls as the WAL grows. SQLite frames the checkpoint interval as a trade-off: frequent checkpoints favor read speed, infrequent checkpoints favor write speed, and the default of 1000 pages is a starting point.
H84 (run 3): An application that must control checkpoint timing can turn off automatic checkpoints (PRAGMA wal_autocheckpoint=0) and run checkpoints from a separate thread or process, for example while idle. SQLite documents this pattern. Syncthing runs a timer-based application checkpointer, and Litestream triggers checkpoints itself.
H85 (run 3): Litestream keeps a long-running read transaction open so that no other process can checkpoint and restart the WAL. It reads new WAL pages continuously and calls SQLite itself to checkpoint when needed. A contributor in a 2023 issue confirms the read transaction is deliberate: it prevents application checkpoints.
H86 (run 3): If an application checkpoint wins the race against Litestream, a December 2023 Litestream issue says Litestream forces a new generation and takes a full snapshot to stay consistent. The issue page names no Litestream version, so this may describe the v0.3 generation model rather than v0.5.
H87 (run 3): Litestream's documented defaults (v0.5.x docs): checkpoint-interval 1m (PASSIVE, runs only if the WAL has at least 1 page), min-checkpoint-page-count 1000 pages (about 4 MB, PASSIVE), and truncate-page-n 121359 pages (about 500 MB). A PASSIVE checkpoint that returns SQLITE_BUSY is skipped and logged. Since v0.5.15, crossing truncate-page-n tries a PASSIVE restart first and forces a blocking TRUNCATE only if the WAL stays above the threshold.
H88 (run 3): Litestream's forced TRUNCATE waits for all active readers and writers and takes a boundary snapshot while holding the write lock, which can stall writers on large databases. The guide warns that long-lived read transactions cause extended blocking. Setting truncate-page-n to 0 disables the emergency TRUNCATE, and the WAL can then grow unbounded if read transactions prevent checkpointing. truncate-page-n bounds WAL growth but does not guarantee the -wal file shrinks; the file keeps its high-water size after a passive restart.
H89 (run 3): Firefox compiles in SQLITE_DEFAULT_JOURNAL_SIZE_LIMIT = 1572864 bytes (1.5 MiB), and its Places database uses 4 MiB, so journal and WAL files are truncated to that limit and kept instead of being deleted (Mozilla Bug 1820478). Firefox still sets wal_autocheckpoint per database. SQLite compares the WAL size with journal_size_limit at each commit and WAL reset and truncates the file if it is larger.
H90 (run 3): To bound the WAL under constant read load, SQLite's WAL guide offers two options: create reader gaps (times with no active reader) in which PASSIVE checkpoints can finish, or run RESTART or TRUNCATE checkpoints, which finish before they return but can block readers while they run. Litestream's emergency tier uses the same escalation: PASSIVE first, then a blocking TRUNCATE only if the WAL stays above its threshold.
H91 (run 3): Do not turn off automatic checkpoints unless something else checkpoints reliably. SQLite's guide says nothing then prevents the WAL from growing excessively. Syncthing found that a timer-based checkpointer may never hit a moment with no active reader, and that leaving SQLite's own auto-checkpoint enabled blocked its own checkpointer because only one checkpoint can run at a time.
H92 (run 3): Do not hold a read transaction open across slow work. Syncthing's maintainer wrote that if a transaction is open for hours, SQLite cannot remove pages written to the WAL after the transaction started, and the WAL 'will grow indefinitely until we're able to complete a checkpoint'. Litestream's guide warns that long-lived read transactions cause extended blocking when it forces a TRUNCATE.
H93 (run 3): Symptom: PRAGMA wal_checkpoint(RESTART) returns SQLITE_BUSY almost instantly even though busy_timeout is 10 seconds (SQLite forum thread 'PRAGMA wal_checkpoint(RESTART) unexpectedly returning SQLITE_BUSY immediately', 2021). Cause: another checkpoint is already running, for example an automatic checkpoint started by another connection's commit. The busy handler covers waiting for readers and writers, not the checkpoint lock. Fix reported in the thread: run PRAGMA wal_autocheckpoint=0 on every connection.
H94 (run 3): If the busy handler returns 0 while a FULL, RESTART or TRUNCATE checkpoint waits for the writer lock or for readers, the checkpoint continues as a PASSIVE one and the call returns SQLITE_BUSY (pragma column 1 = 1). A TRUNCATE checkpoint truncates the WAL only on successful completion, so a busy result means the file was not truncated.
H95 (run 3): VACUUM in WAL mode writes the whole rebuilt database into the WAL as one transaction, and SQLite cannot reset the WAL in the middle of a transaction, so the -wal file stays large afterwards. Run PRAGMA wal_checkpoint(TRUNCATE) after the VACUUM to give the space back.
H96 (run 3): WAL-reset bug: in WAL mode, a data race between a checkpoint and a write transaction can make a later checkpoint skip parts of a committed transaction, so those pages never reach the database file and the file goes corrupt. It needs two or more connections (separate threads or processes) that write or checkpoint at the same instant. SQLite's WAL page says it is likely present in every release from 3.7.0 (2010-07-21) through 3.51.2 (2026-01-09) and is fixed in 3.51.3 (2026-03-13) and later. The 3.53.0 notes (2026-04-09) list the fix too. Release 3.52.0 (2026-03-06) is marked withdrawn, with its features moved to 3.53.0. The newest release on the change log at verification was 3.54.1 (2026-10-16).
H97 (run 3): SQLite's WAL page names backports of the WAL-reset fix for older branches: 3.44.6 and 3.50.7. The SQLite release history page does not list those two versions, so only the WAL page supports them.
H98 (run 3): SQLite describes the WAL-reset bug as rare: its developers could not trigger it organically and needed a test hook until Phil Eaton supplied a reproducer that needs none, and the page says the bug is not an emergency. Antithesis calls it a data race with tight timing constraints that is unlikely in common use. The Register quotes SQLite as saying the bug is extremely unlikely in ordinary use but has serious consequences.
H99 (run 3): Per Antithesis's own account (2026-08-12), a generic workload of concurrent WAL inserts and checkpoints reproduced the WAL-reset bug on SQLite 3.51.2 in about 15 minutes, and the same workload on 3.51.3 came back clean.
H100 (run 3): The Register (2026-08-12) reports that Tailscale's control plane used manual checkpoints, which it calls the rare exception that exposed the WAL-reset bug, and that Tailscale's backups began detecting database corruption in August 2025 with no obvious common trigger.
H101 (run 3): Phil Eaton's analysis (2026-08-23): the checkpointer reads a stale nBackfill value and computes its window against an old mxFrame, while a writer restarts the log and resets nBackfill to 0 inside that window. A large database widens the window because the checkpointer unmaps the database file inside it. He says the outcome is more often data loss than corruption and that SQLite, even after the fix, does not guard against lost writes.
H102 (run 4): A checkpoint copies committed WAL content back into the main database file. SQLite runs one automatically, on the thread that did the COMMIT, when the WAL holds N or more frames after a commit. The default N is 1000 pages (compile-time SQLITE_DEFAULT_WAL_AUTOCHECKPOINT), and every new connection starts with it.
H103 (run 4): Automatic checkpoints are always PASSIVE. So are sqlite3_wal_checkpoint() and PRAGMA wal_checkpoint with no argument. FULL, RESTART and TRUNCATE are available only through sqlite3_wal_checkpoint_v2() and PRAGMA wal_checkpoint(MODE).
H104 (run 4): PASSIVE copies as many frames as it can without waiting for any reader or writer and never calls the busy handler, so it can leave work undone. FULL waits until no writer is active and every reader uses the newest snapshot, then copies all frames and syncs the database file. RESTART does the same, then also waits until all readers read from the database file only, so the next writer restarts the log from the beginning. TRUNCATE does what RESTART does, then truncates the WAL file to zero bytes just before it returns success.
H105 (run 4): The C API and pragma pages say a pending FULL or RESTART checkpoint blocks new writers but lets readers continue; TRUNCATE adds only the final truncation. The WAL guide disagrees about readers (see disagreements).
H106 (run 4): Every checkpoint call first takes the exclusive checkpoint lock (WAL_CKPT_LOCK). If another connection is already checkpointing, the call returns SQLITE_BUSY at once and never invokes the busy handler, even if one is set. FULL, RESTART and TRUNCATE also take the writer lock and do use the busy handler. If no busy handler is set, or it returns 0 before the writer lock is obtained or while waiting for readers, the call continues as PASSIVE and returns SQLITE_BUSY.
H107 (run 4): The WAL restarts from frame 1 only when every frame has been copied back (nBackfill equals mxFrame) and no connection holds a read lock on WAL_READ_LOCK(N) for N greater than 0. The next writer performs the restart and sets nBackfill back to 0. RESTART and TRUNCATE exist to wait for that condition.
H108 (run 4): A checkpoint may copy only frames that no current reader still needs. It stops at the first WAL page that lies past the end mark of any current reader (the WAL-index tracks these as read-marks), and a later checkpoint resumes from where it stopped. If a reader's read-mark is behind the last frame (mxFrame), the checkpoint cannot run to completion.
H109 (run 4): Checkpoint starvation: if a database always has at least one active reader, with read transactions overlapping, no checkpoint can finish or reset the WAL, and the -wal file grows without bound. The cost is disk space and slower reads. Open read transactions are the usual cause.
H110 (run 4): A checkpoint does not normally shrink the -wal file. SQLite recycles it, so the file stays at its high-water size until a TRUNCATE checkpoint runs, or until journal_size_limit (default -1, no limit) makes SQLite truncate the leftover file when a transaction commits or the WAL resets. Setting journal_size_limit to 0 always truncates to the minimum size.
H111 (run 4): In WAL mode with synchronous=NORMAL, commits issue no syncs and the checkpoint is the only operation that does: SQLite syncs the WAL before copying frames into the database and syncs the database file when the checkpoint completes. A transaction committed this way might roll back after a power loss or crash, but WAL mode stays safe from corruption. With synchronous=FULL the writer also syncs the WAL on every commit.
H112 (run 4): When the last connection to a WAL database closes, that connection runs one last checkpoint and deletes the WAL and its shared-memory file. SQLITE_DBCONFIG_NO_CKPT_ON_CLOSE overrides this checkpoint-on-close default.
H113 (run 4): Read performance deteriorates as the WAL file grows, so checkpoints must run regularly. An unbounded WAL costs both disk space and speed.
H114 (run 4): Commits are cheap because they append sequentially and write each page once. Checkpoints are slower than commits because they need syncs and more seeking. Frequent checkpoints favour readers; infrequent ones favour writers.
H115 (run 4): PRAGMA wal_checkpoint returns one row of three integers: busy, log and checkpointed. busy is 1 if a RESTART, FULL or TRUNCATE checkpoint was blocked from completing (the C call would return SQLITE_BUSY). log is the number of pages in the WAL. checkpointed is the number of WAL pages moved back into the database file. log and checkpointed are -1 when the database has no WAL. The C API reports the same counts as pnLog and pnCkpt, both 0 after a successful TRUNCATE.
H116 (run 4): NOOP mode (PRAGMA wal_checkpoint=NOOP, SQLITE_CHECKPOINT_NOOP) checkpoints zero frames and exists only to read the log and checkpointed counts. SQLite 3.51.0 (2025-11-04) added it.
H117 (run 4): sqlite3_wal_hook() registers one callback per connection. SQLite calls it after each commit, once the write lock is released, with the database name and the number of pages now in the WAL. Registering a hook replaces the built-in autocheckpoint; calling sqlite3_wal_autocheckpoint() or PRAGMA wal_autocheckpoint replaces any hook; a threshold of zero or less, or a NULL hook, turns automatic checkpointing off. With a custom hook the application must call sqlite3_wal_checkpoint_v2() or PRAGMA wal_checkpoint periodically so the WAL does not grow without bound.
H118 (run 4): sqlite3_wal_checkpoint_v2() with a NULL or empty schema name checkpoints every attached WAL database and leaves pnLog and pnCkpt undefined. If one database returns SQLITE_BUSY the others still run and SQLITE_BUSY is returned at the end; any other error aborts at once. A named database that is not in WAL mode returns SQLITE_OK with both outputs -1.
H119 (run 4): To find out why a WAL will not shrink, force a checkpoint and read the result row. busy=1 means a blocker stopped a RESTART, FULL or TRUNCATE checkpoint; log larger than checkpointed means frames are still waiting. In a SQLite forum thread (2020-11-11), Simon Slavin advised that if a forced checkpoint does not shrink the WAL, 'something is preventing checkpointing', probably a statement that was never finalized or reset.
H120 (run 4): Checkpoint-race damage is found only by explicit checks. The Antithesis workload asserted 'no lost committed writes' and 'database is not corrupt'. Tailscale's backups detected corruption repeatedly from August 2025 (The Register), and theconsensus.dev says Tailscale caught it with PRAGMA integrity_check, partly by luck, because the bug often loses data without corrupting the file.
H121 (run 4): SQLite's WAL guide says an application can turn off automatic checkpoints and run checkpoints at idle moments or in a separate thread or process, so the thread doing queries and updates never blocks on a sync. The cost is that nothing then stops the WAL growing excessively, so the application must keep checkpointing and watch the WAL size. sqlite3_wal_hook documents the same duty for custom hooks.
H122 (run 4): For workloads with many overlapping readers, SQLite suggests manual checkpoints with SQLITE_CHECKPOINT_RESTART or SQLITE_CHECKPOINT_TRUNCATE, which run to completion before returning. The better-sqlite3 guide shows a 5000 ms timer that checks the -wal file size and runs PRAGMA wal_checkpoint(RESTART) once it passes an application-chosen threshold; the guide gives no threshold value.
H123 (run 4): SQLite's other remedy for starvation is 'reader gaps': times when no process is reading, with checkpoints attempted during those times. A timer-based checkpointer can miss every gap: Syncthing's developers wrote 'we might never hit a timewindow without an active reader'.
H124 (run 4): Litestream takes over checkpointing. It holds a long-running read transaction so no other process can checkpoint and restart the WAL, reads new WAL pages continuously, and calls SQLite to checkpoint when needed. The docs describe v0.5.x (LTX files) and carry no date.
H125 (run 4): Litestream's tips page says it needs periodic but short write locks while it checkpoints, and recommends PRAGMA busy_timeout = 5000 (5 seconds) in the application.
H126 (run 4): For high write loads, Litestream's tips page recommends PRAGMA wal_autocheckpoint = 0, because an application checkpoint between Litestream's checkpoints can make Litestream miss a WAL update; when it detects this it takes a fresh full snapshot. The page says checkpoint detection improvements in v0.5.0 and later reduce the need for snapshots. In issue 547 (opened 2023-12-19), hifi tested removing Litestream's read lock and found that recovery still worked, with the remote never corrupted.
H127 (run 4): Litestream v0.5.x documents a three-tier checkpoint scheme: checkpoint-interval 1m (PASSIVE), min-checkpoint-page-count 1000 pages, about 4 MB (PASSIVE), and truncate-page-n 121359 pages, about 500 MB (PASSIVE first, TRUNCATE only if needed; 0 disables it). A forced TRUNCATE waits for all readers and writers and takes a full boundary snapshot while holding the write lock, which can stall writers on a large database. For workloads with long-lived readers the guide recommends truncate-page-n: 0 and disk monitoring.
H128 (run 4): Syncthing developers (forum thread of 2026-02-06) found the WAL can reach multiple gigabytes when long transactions pin pages and their timer-based checkpointer finds no quiet window. They proposed moving the checkpoint heuristic into the connection pool, so releasing a connection can trigger a checkpoint, and allowing WAL truncation with exclusive locking once the WAL is critically large. Both were proposals, not shipped changes.
H129 (run 4): Turning off automatic checkpoints, or installing a WAL hook that never checkpoints, without a replacement checkpointer lets the WAL grow without bound. Litestream issue 547 notes that an application which disables autocheckpoint for Litestream's sake leaves users who do not run Litestream with 'an endlessly growing WAL'.
H130 (run 4): Statements that are never reset or finalized can hold transactions open and block checkpoints. Richard Hipp wrote (2021-04-06) that with unreset write statements 'you will likely be leaving some transactions open, which will prevent the checkpoint from happening'. In a 2020-11 thread, Simon Slavin pointed to a step() that was never finalized or reset, and Gunter Hick listed open read transactions, large write transactions and disabled checkpointing as reasons a checkpoint cannot finish.
H131 (run 4): A large write transaction can push the WAL well past the autocheckpoint threshold, because SQLite checks the threshold only after a commit. Forum contributors name large write transactions as a reason checkpoints cannot keep the WAL small, and one says the WAL size is roughly bounded by the autocheckpoint size plus the largest transaction.
H132 (run 4): journal_size_limit is not a cap on WAL growth. SQLite applies it at commit and WAL reset, so it cannot shrink a WAL that still holds frames waiting for a checkpoint. In a 2020-11 forum thread a user set journal_size_limit and still saw the WAL reach about 1.5 to 2 GB under sustained writes; Gunter Hick replied that the limit 'only applies to an empty journal file'.
H133 (run 4): Running your own checkpointer next to SQLite's autocheckpoint lets the two collide. Checkpoints take an exclusive lock, and a second checkpoint gets SQLITE_BUSY without the busy handler running. Syncthing's developers wrote 'we're blocking our own checkpointer' because they left autocheckpoint on.
H134 (run 4): The WAL-reset bug is a data race between a checkpoint and a write that resets the WAL. SQLite says it is likely present in every version from 3.7.0 (2010-07-21) through 3.51.2 (2026-01-09) and is fixed in 3.51.3 (2026-03-13) and later. Antithesis reports that 3.51.2 still failed its workload and 3.51.3 came back clean.
H135 (run 4): SQLite's WAL guide lists backports of the WAL-reset fix for older release lines: 3.44.6 and 3.50.7.
H136 (run 4): SQLite 3.52.0 (2026-03-06) included the WAL-reset fix but was withdrawn because some new features were not fully compatible with prior releases. SQLite released 3.51.3 (2026-03-13) in its place with the WAL-reset fix and minor fixes. 3.53.0 (2026-04-09) re-released 3.52.0 with extra changes for stale expression indexes and is the first major release that contains the fix.
H137 (run 4): Mechanism, per SQLite: a second checkpoint starts just after a first one finishes; another connection commits a transaction that resets the WAL; because of a data race the second checkpoint misses the reset and sets a wal-index header field incorrectly; a later checkpoint then skips part of the reset transaction, which can corrupt the database file. It needs WAL mode and two or more connections, in separate threads or processes, writing or checkpointing at the same instant.
H138 (run 4): theconsensus.dev traces the lost frames to a stale mxFrame: the checkpointer reads the header, a writer then restarts the log (walRestartHdr sets mxFrame to 0, bumps the salt and sets nBackfill to 0), and the checkpointer then sets nBackfill to its stale mxFrame, so new frames 1..N count as already copied. The post's roughly 100-line C reproducer (walrace.c, public API only) produced lost writes and sometimes corruption within seconds on 3.51.2 and none on 3.53.0, using a large database, a 1 GB mmap_size and a concurrent writer to widen the race window.
H139 (run 4): SQLite rates the WAL-reset bug as unlikely in common use and advises upgrading to a fixed version, saying it is not an emergency. The Register reports the SQLite team calls it 'incredibly unlikely to happen in most situations' and recommends updating.
H140 (run 4): SQLite's WAL guide says its developers could not reproduce the bug without a test-only hook, that telemetry puts the occurrence rate at or below the expected rate of SSD malfunctions or cosmic-ray hits, and that an update dated 2026-08-24 mentions a reproducer that needs no hook.
H141 (run 4): Two independent write-ups reproduced the bug on 3.51.2 with workloads that write and checkpoint concurrently: Antithesis reports its first run found it in 15 minutes, and theconsensus.dev's C program lost writes within seconds. Antithesis is a testing vendor and the C program is tuned to widen the race, so neither measures how often ordinary applications hit it.
H142 (run 4): Tailscale's repeated database corruption, first detected by backups in August 2025 with no obvious common trigger, led the SQLite team to the WAL-reset bug. Antithesis calls it 6 months of shaky uptime for Tailscale.
H143 (run 4): The Register quotes Tailscale's Alex Chan: 'we take manual control of the checkpoint process so we can run fast and consistent backups', and calls Tailscale's manual checkpointing a rare exception to standard SQLite use. The article states no checkpoint mode or frequency.
H144 (run 5): A checkpoint copies committed pages from the WAL file back into the main database file. A WAL database therefore has three primitive operations: read, write and checkpoint. The checkpoint's progress is the wal-index field nBackfill, the number of WAL frames already backfilled into the database. When nBackfill equals mxFrame, the whole WAL is in the database file.
H145 (run 5): SQLite checkpoints automatically in two cases: after any COMMIT that leaves the WAL at 1000 pages or more, and when the last connection to the database closes. A connection changes the 1000-page default with PRAGMA wal_autocheckpoint=N, and a build changes it with SQLITE_DEFAULT_WAL_AUTOCHECKPOINT. Every automatic checkpoint is PASSIVE. The thread that issues the triggering COMMIT runs the checkpoint, so most commits stay fast and an occasional commit is much slower.
H146 (run 5): The 1000-page threshold counts pages, not bytes. SQLite's WAL guide and Litestream's guide both call it about 4 MB, which matches 4096-byte pages (1000 x 4096 bytes). Other page sizes scale the byte size in proportion. Android's framework config describes database pages as typically 1 to 4 KB.
H147 (run 5): An explicit checkpoint uses sqlite3_wal_checkpoint_v2() or PRAGMA wal_checkpoint(mode), and any writable connection can start one. PASSIVE checkpoints as many frames as it can without waiting for any reader or writer, never calls the busy handler, and may stop early. FULL waits (calling the busy handler) until no writer is active and all readers use the newest snapshot, then checkpoints every frame and syncs the database file. RESTART does what FULL does, then waits until all readers read only from the database file, so the next writer restarts the log at the beginning. TRUNCATE does what RESTART does, then truncates the WAL file to zero bytes just before it returns success. NOOP (added in SQLite 3.51.0, 2025-11-04) checkpoints zero frames and only returns the counters. Plain sqlite3_wal_checkpoint() and a bare PRAGMA wal_checkpoint are PASSIVE.
H148 (run 5): Every checkpoint, automatic or explicit, takes an exclusive checkpoint lock (WAL_CKPT_LOCK in the wal-index). If another connection already holds that lock, the call returns SQLITE_BUSY at once and does not call the busy handler. FULL, RESTART and TRUNCATE also take the exclusive writer lock, so they block new writers while pending. If the busy handler returns 0 before the writer lock is held or while waiting for readers, the checkpoint continues as PASSIVE and returns SQLITE_BUSY.
H149 (run 5): Each reader fixes an end mark: the last valid commit in the WAL when its read began. A checkpoint can run beside readers, but it must stop at the first WAL page past the end mark of any current reader, because it would otherwise overwrite database content that reader is using. The checkpoint stores how far it got in the wal-index and resumes from there on its next run. A long-running read transaction therefore blocks checkpoint progress. Syncthing's developers put it this way: 'If a transaction is open for hours, we can't remove pages written to the WAL after its start.'
H150 (run 5): The WAL file restarts only when a checkpoint has copied the whole WAL into the database and synced it, and no reader is using the WAL. The next writer then rewinds to the start of the file and writes new frames over the old ones. This reset keeps the WAL from growing without bound. A write transaction in progress also blocks the reset, so one very large write transaction produces a large WAL until it commits and a checkpoint completes.
H151 (run 5): A completed checkpoint does not normally make the -wal file smaller. SQLite reuses the existing file from its start because overwriting is faster than appending. The file shrinks in two cases. If PRAGMA journal_size_limit holds a limit, SQLite compares the file size to the limit at each commit and WAL reset and truncates the file down to the limit (default -1 means no limit; 0 truncates to the minimum). A successful TRUNCATE checkpoint cuts the file to zero bytes. Litestream's guide confirms that a passive restart does not shrink the physical -wal file.
H152 (run 5): Checkpoints perform the fsyncs that make WAL data safe. SQLite syncs the WAL before its content moves into the database, and syncs the database file before the WAL resets. With synchronous=NORMAL in WAL mode, commits do not sync. SQLite then syncs the WAL before each checkpoint, the database file after each completed checkpoint, and the WAL header when the WAL is reused after a checkpoint. A transaction committed under NORMAL can roll back after a power loss or OS crash. synchronous=FULL adds a WAL sync after every commit.
H153 (run 5): Checkpoint progress (nBackfill) lives in the wal-index shared memory. SQLite never syncs the wal-index and deletes its file when the last connection closes. Crash recovery rebuilds the wal-index by scanning the WAL and sets nBackfill to zero, so the next checkpoint treats no frame as backfilled.
H154 (run 5): Checkpoint frequency trades read speed against write speed. A reader checks the WAL for each page it needs, so read cost grows with WAL size. A checkpoint is slower than a write transaction because it syncs and seeks. Frequent checkpoints keep reads fast. Infrequent checkpoints spread each checkpoint's cost over more writes. SQLite calls its 1000-page default a setting that worked well in tests on workstations and says other platforms or workloads may need other values. Android's framework config adds that a bigger WAL makes each checkpoint take longer.
H155 (run 5): To test a checkpoint-related change or hunt a checkpoint race, run a workload in which one connection commits while another checkpoints, then check two invariants: every committed row is still readable after a TRUNCATE checkpoint, and the database passes an integrity check. Antithesis used generic assertions of this kind, found the WAL-reset bug on its first run in 15 minutes on SQLite 3.51.2, and got a clean run of the same workload on 3.51.3. Phil Eaton's 100-line C program checks the same kind of invariants and loses a transaction within seconds.
H156 (run 5): To keep checkpoint cost off the commit path, an application can set wal_autocheckpoint to 0 (or install its own wal_hook) and run checkpoints from another thread or process during idle moments. With synchronous=NORMAL the main thread then never waits on fsync, at the price of durability after a power loss. dqlite works this way: it disables automatic checkpoints, blocks user-initiated ones, and runs its own stop-the-world TRUNCATE checkpoint. Litestream also runs the checkpoints itself. The application then owns the job of keeping the WAL bounded.
H157 (run 5): Litestream, which replicates the WAL, takes over checkpointing. It holds a long-running read transaction so no other process can checkpoint and restart the WAL, and it calls SQLite to checkpoint when needed. Its v0.5.x guide describes three tiers, checked in this order after each sync: an emergency tier at 121359 pages (truncate-page-n, about 500 MB) that tries PASSIVE first and forces a blocking TRUNCATE only if the WAL stays above the threshold (passive-first behavior from v0.5.15); a PASSIVE checkpoint at 1000 pages (min-checkpoint-page-count, about 4 MB); and a PASSIVE checkpoint every minute (checkpoint-interval). A forced TRUNCATE waits for all readers and writers and can stall writers.
H158 (run 5): Production embedders set their own WAL limits instead of relying on SQLite's defaults. Android's framework config (main branch) sets db_wal_autocheckpoint to 100 pages, db_journal_size_limit to 524288 bytes and db_wal_sync_mode to NORMAL. A 2023 Firefox commit (Bug 1820478, 2023-05-12) builds its bundled SQLite with SQLITE_DEFAULT_JOURNAL_SIZE_LIMIT=1572864 bytes (the Places database uses 4 MiB) and, in early-beta-or-earlier builds, persists the -wal and -shm files, relying on the size limit so the WAL is truncated rather than deleted at shutdown.
H159 (run 5): dqlite is not affected by the WAL-reset bug. Its VFS takes the write lock for both appending and checkpointing, so the two cannot run at the same time and there is no data race. A TLA+ model of SQLite's locking found the bug's counterexample in 20 states, and with dqlite's extra lock the model checker reports no error. SQLite's own trigger conditions (two connections writing or checkpointing at the same instant) agree with this reasoning.
H160 (run 5): sqlite3_wal_autocheckpoint(D,N) is a thin wrapper around sqlite3_wal_hook(), and the two share one callback slot: registering either one replaces the other. A WAL hook runs after each commit, after the write lock is released, and receives the database name and the number of pages now in the WAL (including the pages just committed). A NULL hook, or N of zero or less, turns automatic checkpointing off entirely. sqlite3_wal_autocheckpoint(db, 1000) restores the default.
H161 (run 5): PRAGMA wal_checkpoint returns one row of three integers. The first is 0, or 1 when a FULL, RESTART or TRUNCATE checkpoint was blocked (the equivalent C call would return SQLITE_BUSY). The second is the number of modified pages in the WAL. The third is the number of WAL pages moved back into the database. The second and third are -1 when the database has no WAL, and both are 0 after a successful TRUNCATE. By the lock rules, a gap between the second and third values means readers or writers kept part of the WAL from being backfilled. The NOOP mode returns these counters without checkpointing any frame.
H162 (run 5): When the last connection to a WAL database closes, it checkpoints and deletes the -wal and -shm files. SQLITE_DBCONFIG_NO_CKPT_ON_CLOSE turns off that checkpoint. If the last process exits without closing cleanly, or SQLITE_FCNTL_PERSIST_WAL is in use, the WAL file stays on disk. A database file separated from its WAL can lose committed transactions or become corrupt, so the WAL must travel with the database.
H163 (run 5): Three setups let the WAL grow without bound. First, automatic checkpoints are disabled and nothing else checkpoints. Second, checkpoint starvation: overlapping readers mean at least one reader is always active, so no checkpoint can finish or reset the WAL. Third, a very large write transaction blocks the reset until it commits. SQLite's remedies are to leave reader gaps and checkpoint in them, and, where many readers overlap, to run manual RESTART or TRUNCATE checkpoints, accepting that readers may block. Litestream's guide adds an emergency truncate tier as a brake against runaway growth, and Syncthing's developers expect database operations to 'grind to a halt' once the WAL reaches multiple gigabytes.
H164 (run 5): Running your own checkpointer next to SQLite's automatic one invites SQLITE_BUSY. Syncthing's developers noted (forum post, 2026-02-06) that they do not disable SQLite's automatic checkpoint, so a commit at 1000 pages triggers a passive checkpoint, and because checkpoints of any kind are exclusive, 'we're blocking our own checkpointer'. They also noted that their timer-based checkpointer needs a point of 'radio silence' in database use. SQLite's C API documents the mechanism: a second checkpointer gets SQLITE_BUSY immediately, without a busy-handler retry.
H165 (run 5): Older SQLite advice on WAL and large transactions is out of date. SQLite's WAL page still shows, struck through, the claims that WAL works best with small transactions and that rollback-journal mode is faster above about 100 MB. Since SQLite 3.11.0 (2016-02-15), WAL works efficiently with transactions larger than the cache size, and one transaction's WAL is roughly proportional to its size. A large write transaction still keeps the WAL from resetting until it commits and a checkpoint completes.
H166 (run 5): If wal_checkpoint(TRUNCATE), FULL or RESTART returns busy=1 or SQLITE_BUSY, the checkpoint did not finish. When the busy handler gives up, the call falls back to PASSIVE behavior. TRUNCATE cuts the file only just before a successful return, so the -wal file keeps its size. Find and end long read transactions, then retry. A forced TRUNCATE that waits on long readers can itself stall writers, as Litestream's guide warns.
H167 (run 5): The WAL-reset bug is a data race between a checkpoint and a commit that resets the WAL, and it can corrupt a WAL-mode database. SQLite developer Dan found and fixed it on 2026-03-03. It is likely present in every release from 3.7.0 (2010-07-21) through 3.51.2 (2026-01-09). It is fixed in 3.51.3 (2026-03-13) and later, with backports in 3.44.6 and 3.50.7. It needs WAL mode, two or more connections on the same file in separate threads or processes, and a write and a checkpoint at the same instant. SQLite advises upgrading but says this is 'not an emergency'.
H168 (run 5): Mechanism of the WAL-reset bug: a first checkpoint copies the whole WAL; a second checkpoint starts and reads the wal-index header; a commit on another connection resets the WAL and writes new frames at its start; the second checkpoint does not notice the reset and leaves nBackfill claiming frames are backfilled that are not; after more commits a later checkpoint skips part of the post-reset transaction, so those pages never reach the database file. In Phil Eaton's trace the checkpointer reads mxFrame=360, the writer resets mxFrame to 0, bumps the salt, sets nBackfill=0 and commits 5 frames, then the checkpointer sets nBackfill=360. The fix compares the live WAL salt with the salt read at checkpoint start and skips the checkpoint if the WAL was reset. Canonical calls it a single extra check.
H169 (run 5): Sources disagree on how rare the WAL-reset bug is. SQLite's developers could not trigger it organically, needed a special test hook, and put its field rate at or below SSD malfunctions and cosmic-ray hits. Canonical also calls its real-world impact very low. Yet Tailscale reported 19 corruption incidents over about six months starting August 2025 (Techzine), Phil Eaton's 100-line C program (two threads, three connections, public API only) loses a transaction within seconds on 3.51.2, and Antithesis found the bug in 15 minutes with a plain concurrent write-and-checkpoint workload. The two views fit together if the trigger needs checkpoints and commits racing in a tight loop on separate connections.
H170 (run 5): Press reports say Tailscale was more exposed to the WAL-reset bug because it took manual control of checkpointing, running checkpoints at its own relatively aggressive pace so it could take fast, consistent backups. The Register quotes Tailscale's Alex Chan: 'we stepped off the well-trodden operational path'. Both outlets relay Tailscale's own account, and the primary Tailscale post was not readable in this run.
H171 (run 5): SQLite 3.52.0 (2026-03-06) is marked withdrawn on SQLite's release page, and its planned features moved to 3.53.0. SQLite 3.51.3 (2026-03-13) lists one WAL change: 'Fix the WAL-reset database corruption bug.' Techzine reports that Tailscale saw apparent corruption in 13 databases on the release that first carried the fix. That was a false alarm: a separate change to floating-point rounding made existing indexes look corrupt.
H172 (run 5): Phil Eaton's reproducer races a PASSIVE checkpoint against a writer. It makes explicit sqlite3_wal_checkpoint_v2 PASSIVE calls on a helper connection, commits from a burst thread during the checkpoint window, and uses TRUNCATE only for cleanup. The automatic checkpointer is also PASSIVE-only. His article does not test FULL or RESTART. The same program loses a transaction on SQLite 3.51.2 within seconds and loses none on 3.53.0.
