SET F:
F1: A checkpoint copies committed WAL frames into the main database file. When several frames hold versions of the same page, only the newest version is written; superseded versions are skipped.
F2: A checkpoint runs concurrently with readers but must stop at the first WAL frame past the end mark of any active reader, because copying it would overwrite database pages that reader is still using. The checkpointer records its progress in the wal-index and resumes from that point on the next call, so a read transaction that stays open for hours pins every WAL page written after it started.
F3: The WAL is reset, not truncated, by default: once every frame has been checkpointed and synced and no reader is still using the WAL, the next writer rewinds to the start of the file and overwrites old frames. A new salt in the WAL header makes stale frames with the old salt invalid, and the header's checkpoint sequence number increments. The -wal file only shrinks when journal_size_limit is set or a TRUNCATE checkpoint runs.
F4: Automatic checkpoints are PASSIVE and run inside the committing connection, in the committing thread, when a COMMIT leaves the WAL at or above wal_autocheckpoint pages. The default is 1000 pages (compile-time SQLITE_DEFAULT_WAL_AUTOCHECKPOINT), roughly 4 MB at the default 4096-byte page size. The setting is per connection; zero or a negative value disables it for that connection only.
F5: When the last connection to a WAL-mode database closes, SQLite runs a final checkpoint and then deletes the -wal and -shm files. With auto-checkpoint disabled, nothing else bounds WAL growth.
F6: sqlite3_wal_checkpoint_v2() and PRAGMA wal_checkpoint accept five modes. PASSIVE copies as many frames as it can without waiting and never calls the busy handler. FULL waits for the current writer to finish and for all readers to reach the latest snapshot, then copies every frame and syncs the database. RESTART does FULL and then waits until no reader uses the WAL, so the next writer restarts the log from the beginning. TRUNCATE does RESTART and then truncates the -wal file to zero bytes. NOOP, added in SQLite 3.51.0, checkpoints nothing and only reports the frame counts.
F7: FULL, RESTART and TRUNCATE take the exclusive writer lock and invoke the busy handler while waiting for the lock and for readers. They block new writers while pending but let new readers proceed unimpeded. If the busy handler gives up, the call completes what it can like PASSIVE and returns SQLITE_BUSY; the pragma reports this as busy=1 in its first column.
F8: Every checkpoint call first takes an exclusive checkpoint lock. If another connection or process already holds it, the call returns SQLITE_BUSY at once without invoking the busy handler. Checkpoints are therefore mutually exclusive, and a 1000-page auto-checkpoint from any connection can make an application's own RESTART or TRUNCATE checkpoint fail with SQLITE_BUSY.
F9: PRAGMA wal_checkpoint returns one row with three columns: busy (0, or 1 if a FULL, RESTART or TRUNCATE checkpoint was blocked), log (frames in the WAL) and checkpointed (frames moved into the database so far). If the database is not in WAL mode the last two columns are -1 and the pragma is a no-op. After a successful TRUNCATE both counts are 0. Ignoring the busy column hides failed checkpoints, which Syncthing found it had been doing.
F10: With PRAGMA synchronous=NORMAL in WAL mode the checkpoint is the only sync point: the WAL is fsynced before each checkpoint, the database file after each completed checkpoint, and the WAL header when the file is reused, while ordinary commits do no fsync. synchronous=FULL adds a WAL fsync after every commit; EXTRA is identical to FULL in WAL mode. Litestream recommends NORMAL for this reason.
F11: Checkpoints cost more than write transactions because they fsync and seek, and read performance falls as the WAL grows because readers must search it. Frequent checkpoints favour reads; infrequent ones favour writes. Because the committing thread runs auto-checkpoints, most commits are fast but some stall on the checkpoint; running checkpoints from a dedicated thread, process or service keeps commits from blocking on fsync.
F12: Checkpoint starvation: if overlapping read transactions ensure there is always at least one active reader, no checkpoint can run to completion and reset the WAL, and the -wal file grows without bound (PASSIVE auto-checkpoints never force the issue). Mitigations are to create reader gaps, keep read transactions short, or issue RESTART or TRUNCATE checkpoints, which wait for readers but can stall writers.
F13: A single prepared SELECT that has been stepped to a row but not stepped to SQLITE_DONE or passed to sqlite3_reset() keeps its read transaction open and alone pins the WAL end mark, so the WAL grows past the 1000-page auto-checkpoint threshold even with one connection. A forum reproducer showed this on SQLite 3.30.0 and 3.38.5; resetting or finishing the statement promptly kept the WAL near 4 MB.
F14: A checkpoint cannot reset the WAL in the middle of a write transaction, so one large transaction produces a WAL at least as large as the transaction. VACUUM in WAL mode writes the whole rebuilt database into the WAL, nearly doubling disk use until a checkpoint runs. Since SQLite 3.11.0 (2016-02-15) a transaction's WAL footprint is proportional to its size; earlier versions could write the same page more than once.
F15: After VACUUM in WAL mode, run PRAGMA wal_checkpoint(TRUNCATE) to move the rebuilt pages into the database and shrink the -wal file; otherwise the space has only moved from the database to the WAL. journal_size_limit does not limit WAL growth during the VACUUM transaction, only after a checkpoint or reset.
F16: PRAGMA journal_size_limit (default -1, no limit) truncates the -wal file down to the limit each time a transaction commits or the WAL resets; 0 always truncates to the minimum. It applies to one database on one connection, so with a connection pool it must be set on the connection that performs the checkpoint. Syncthing saw TRUNCATE shrink the WAL to zero bytes despite journal_size_limit=67108864 because the pragma had been set on a different pooled connection.
F17: sqlite3_wal_hook() registers a callback invoked after each WAL-mode commit with the connection, the database name and the current number of WAL pages; the callback may read, write or checkpoint, and a non-SQLITE_OK return propagates to the caller although the commit has already happened. Auto-checkpoint (the C function and the pragma) is built on this hook and overwrites any earlier hook; registering your own hook, or passing NULL, replaces auto-checkpoint. This is the intended way to implement custom checkpoint policy.
F18: Passing NULL or an empty string as zDb to sqlite3_wal_checkpoint_v2() checkpoints every attached WAL database; pnLog and pnCkpt are then undefined, SQLITE_BUSY on one database does not stop the others, and SQLITE_BUSY is returned at the end. Naming a non-WAL database returns SQLITE_OK with both counts -1; naming an unknown database returns SQLITE_ERROR.
F19: Litestream holds a long-running read transaction between its own checkpoints so no other process can checkpoint and restart the WAL before it has copied the frames. Under heavy write load (tens of thousands of small writes per second) an application auto-checkpoint can still slip in, after which Litestream takes a fresh full snapshot; it therefore recommends PRAGMA wal_autocheckpoint=0 plus PRAGMA busy_timeout=5000 in the application. v0.5.0+ improved checkpoint detection reduces the snapshot fallback.
F20: Litestream v0.5.x uses a tiered policy: a PASSIVE checkpoint when the WAL exceeds min-checkpoint-page-count (default 1000 pages, about 4 MB) or every checkpoint-interval (default 1m), and an emergency checkpoint when the WAL exceeds truncate-page-n (default 121359 pages, about 500 MB) that tries PASSIVE first and forces TRUNCATE only if the WAL stays above the threshold (passive-first since v0.5.15). A forced TRUNCATE waits for all readers and writers and takes a boundary snapshot under the write lock, so it can stall writers; truncate-page-n=0 avoids blocking but leaves WAL size unbounded.
F21: Syncthing's SQLite backend ran PRAGMA wal_checkpoint(TRUNCATE) every 8 hours with a 64 MiB journal_size_limit while leaving SQLite auto-checkpoints enabled and ignoring the busy column. It hit multi-gigabyte WAL files, diagnosed three causes (hours-long read transactions, near-constant activity leaving no idle window for RESTART or TRUNCATE, and auto-checkpoints colliding with its own checkpointer), and proposed disabling auto-checkpoint, a dedicated checkpointer triggered by WAL size or connection release, and shorter read transactions.
F22: Splitting long read work into short read transactions and issuing PRAGMA wal_checkpoint(RESTART) when starvation is detected cut Syncthing's WAL on a 2.5 GB database from about 2.2 GB to about 128 MiB during index resets (Syncthing PR #10027).
F23: The WAL-reset bug is a data race between a checkpoint and a write transaction that resets the WAL, when two or more connections (separate threads or processes) write or checkpoint at the same instant. The second checkpoint misses the reset and leaves the wal-index backfill count (nBackfill) wrong, so a later checkpoint skips part of a committed transaction: committed pages are never written to the database while pages that reference them are, producing lost writes and a corrupt file. SQLite says it is likely present from 3.7.0 (2010-07-21) through 3.51.2 (2026-01-09); it is fixed in 3.51.3 (2026-03-13) with backports in 3.44.6 and 3.50.7. 3.52.0 also carried the fix but was withdrawn for an unrelated regression.
F24: SQLite describes the WAL-reset race as unlikely in common use and says its developers never reproduced it organically, only with a test hook. Tailscale nevertheless recorded 19 corruption incidents over about six months from August 2025 with a single Go process per shard that checkpoints manually and very aggressively, and Antithesis reproduced it on 3.51.2 in about 15 minutes with a generic workload of concurrent writes and checkpoints; the same workload ran clean on 3.51.3. Tailscale had run four months without incidents as of August 2026.
F25: The 3.51.3 fix is a single extra check: the checkpointer confirms, by comparing the WAL salt, that the WAL was not reset since the checkpoint began. Canonical's TLA+ model found the corrupting trace in about 20 states; dqlite is unaffected because it blocks user-initiated checkpoints, disables automatic ones and runs its own checkpoint as a stop-the-world action under the write lock, so a writer and a checkpoint can never overlap.
F26: Practical hardening for applications that drive checkpoints themselves: upgrade to SQLite 3.51.3 or later; disable auto-checkpoint on every connection if one component owns checkpointing; always check the busy column or SQLITE_BUSY return and retry; run PRAGMA integrity_check on backups continuously; and treat non-standard, aggressive checkpoint schedules as a risk surface, since that is where the WAL-reset race surfaced in production.
