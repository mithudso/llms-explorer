## Definitions

- [statement] The $regex query predicate is not collation-aware, so a case-insensitive index does not accelerate it through case-insensitive collation keys; adding collation to a regex query does not turn it into an indexed collated-equality lookup. (high confidence) — https://www.mongodb.com/docs/manual/core/index-case-insensitive.md · keywords: Collation-based case-insensitive indexes as a $regex alternative · also: https://www.mongodb.com/docs/manual/reference/operator/query/regex.md
- [statement] Collated equality is a scoped alternative for whole-value matching, not a general replacement for prefix, substring, or arbitrary regex patterns. Separately, case-sensitive regex patterns beginning with a simple literal prefix can support index range optimization; that documented optimization should not be assumed for /prefix/i. (high confidence) — https://www.mongodb.com/docs/manual/core/index-case-insensitive.md · keywords: Collation-based case-insensitive indexes as a $regex alternative · also: https://www.mongodb.com/docs/manual/reference/operator/query/regex.md, https://www.codevra.org/mongodb/mongodb-collation-indexes
- [statement] Case insensitivity is a comparison policy, not a blanket equivalence rule for every script or accent. In Codevra's English strength-two example, Ada and ada compare equally while Áda remains distinct; test the application's locale and representative values before replacing regex. (medium confidence) — https://www.mongodb.com/docs/manual/core/index-case-insensitive.md · keywords: Collation-based case-insensitive indexes as a $regex alternative · also: https://www.codevra.org/mongodb/mongodb-collation-indexes

## How it works

- [statement] For whole-value case-insensitive equality, create an index such as {name:1} with collation {locale:'en',strength:2}, and run find({name:'ada'}).collation({locale:'en',strength:2}); this is an alternative when regex was being used only to express case-insensitive equality. (high confidence) — https://www.mongodb.com/docs/manual/core/index-case-insensitive.md · keywords: Collation-based case-insensitive indexes as a $regex alternative · also: https://www.codevra.org/mongodb/mongodb-collation-indexes
- [statement] The incident's published explain results show why IXSCAN alone is insufficient: the collation-index plan examined 1,902,678 documents for one result, while the hinted ordinary-index plan examined the same number of keys but fetched one document. Inspect indexName, bounds, totalKeysExamined, totalDocsExamined and nReturned when evaluating the rewrite. A measured hint to the binary index helped the historical Parse incident, but that workaround does not establish a universal rule for current query planners. ## Comparisons and alternatives

- [statement] For a whole-value lookup whose required equivalence agrees with the chosen locale, use equality with a matching case-insensitive collation instead of encoding equality as a case-insensitive regex. MongoDB documents createIndex({type:1},{collation:{locale:'en',strength:2}}) and find({type:'apple'}).collation({locale:'en',strength:2}) matching apple, Apple, and APPLE through that index. (high confidence) — https://www.mongodb.com/docs/manual/core/index-case-insensitive.md · keywords: Collation-based case-insensitive indexes as a $regex alternative · also: https://www.mongodb.com/community/forums/t/collation-index-best-practice/2189

## Facts and statements

- [statement] String comparisons must use the index's matching collation to benefit from that index. An index's collation alone does not change query comparison rules; collection defaults can supply the collation to both queries and indexes. (high confidence) — https://www.mongodb.com/docs/manual/core/index-case-insensitive.md · keywords: Collation-based case-insensitive indexes as a $regex alternative · also: https://www.codevra.org/mongodb/mongodb-collation-indexes
- [statement] In an April 2020 Parse Server 4.1.0 / MongoDB 3.6.12 incident, operators reported a regex performance regression after adding case-insensitive indexes; hinting the ordinary index restored their prior behavior. This is historical workload evidence, not a claim that current MongoDB releases always select the wrong index. (medium confidence) — https://github.com/parse-community/parse-server/issues/6559 · keywords: Collation-based case-insensitive indexes as a $regex alternative · also: https://www.mongodb.com/community/forums/t/collation-index-best-practice/2189
- [statement] An operation must use the same collation as the index to use that index for the relevant string comparison. Merely creating a case-insensitive index does not make an otherwise binary equality query case-insensitive. (high confidence) — https://www.mongodb.com/docs/manual/core/index-case-insensitive.md · keywords: Collation-based case-insensitive indexes as a $regex alternative · also: https://docs.spring.io/spring-data/mongodb/reference/mongodb/collation.html
- [statement] Queries and subsequently created indexes inherit a collection's default collation unless they explicitly specify a different collation. With no applicable collection default, a query must explicitly supply the matching non-simple collation to benefit from that index's string comparison rules. (high confidence) — https://www.mongodb.com/docs/manual/core/index-case-insensitive.md · keywords: Collation-based case-insensitive indexes as a $regex alternative · also: https://docs.spring.io/spring-data/mongodb/reference/mongodb/collation.html
- [statement] A historical Parse Server 4.1.0 incident on MongoDB 3.6.12 reported a regex query selecting a collated index and slowing down. The accompanying MongoDB forum explain shows IXSCAN plus FETCH with 1,902,678 keys and documents examined for one returned document. This demonstrates that seeing IXSCAN does not itself establish an efficient selective lookup; these are historical observations, not a claim about current server versions.
