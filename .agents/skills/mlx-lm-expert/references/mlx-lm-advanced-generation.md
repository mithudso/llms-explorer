# MLX-LM native multimodal generation and request lifecycle

## Overview

MLX-LM speculative decoding can call a logits processor while evaluating draft and verification tokens, but it may later reject a draft. Trimming token history and rewinding model caches does not rewind arbitrary mutable state inside a processor. The MTP discussion reports thinking-budget drift when verification advances processor state for a token later rejected; it names stateless recomputation or a future save_state()/restore_state() protocol as remedies. The earlier report blaming lazy MLX array evaluation was challenged by a maintainer, so the concern is best scoped to transactional processor state across rejection, not a general lazy-array bug. This matters to constrained decoding and counters because they must follow accepted tokens. Cross-project MTP notes independently state that grammar and sampler state must track the accepted prefix.

MLX-LM exposes text generation as a lazy Python iterator, so request cancellation largely belongs to the code that owns iteration. The current stream_generate signature has no request ID or explicit cancellation token. Closing an entered iterator unwinds its wired-limit context. That context synchronizes streams and restores the prior limit only when the wired-limit helper returned a prior limit; its no-op branch does neither. The stock server has a per-request stop flag as well as a generation-thread stop flag, and its HTTP response handler calls the request stop method in finally. Serving adapters add request IDs and cancellation events, remove batched sequences, and close the underlying iterator. A third-party MLX server issue shows that stopping an async consumer does not automatically stop generation running on a worker thread. Keep per-request generation state, shared prompt-cache entries, and allocator buffers as separate lifecycle layers.

MLX-LM's built-in HTTP server has a processor-backed path for image parts in chat messages. It normalizes remote image URLs to data URLs, decodes RGB pixels, applies the model processor, and passes token IDs plus image embeddings into generation. For the KV prefix cache, it substitutes image patch-token runs with IDs derived from the URI string; the server checks the cache after image processing and embeds only uncached image blocks. The standalone mlx_lm.cache_prompt CLI handles a text prompt and should not be treated as an image cache. Other VLM integrations show that image KV checkpoints and skipping vision encoding require model-specific image boundaries or feature-cache hooks.

## Core Concepts

### MLX-LM stateful logits processor rollback during speculative decoding

- In MTP speculative decoding, a stateful processor can mutate on a candidate token that is later rejected; if its state is not restored or rebuilt from the accepted prefix, grammar or counter state can drift from the generated history.[^c1-7][^c1-2][^c1-8][^c1-9]
- MLX-LM's MTP work corrected stale prev_tokens handling and rejected-draft history separately from processor state. The thinking-budget processor can still advance during verification for a bonus token that is later rejected; the maintainer says recomputing state from accepted token history or adding an explicit save_state()/restore_state() protocol would prevent counter drift. verified-as-of: 2026-10-23[^c1-2][^c1-6][^c1-7][^c1-4]

### MLX-LM native request cancellation and generation resource lifecycle

- In the current upstream snapshot, mlx_lm.generate.stream_generate returns a lazy Python generator and its signature has no request ID or explicit cancellation-token argument; callers must provide cancellation through the code that owns and controls iteration. verified-as-of: 2026-10-23[^c2-1][^c2-2]
- In MLX-LM source at 0d4d3d04f8ab checked on 2026-10-23, stream_generate is a Python generator with no request ID or explicit cancellation-token parameter; generate_step accepts an optional prompt_cache and updates it in place. The stock server distinguishes ResponseGenerator._stop, which stops its generation thread, from per-request GenerationContext._should_stop and stop(). Its generation paths check the request flag, and the HTTP response handler calls ctx.stop() in finally. These mechanisms do not establish a measured disconnect-to-stop latency or immediate interruption of an MLX evaluation already in progress. (two sources) verified-as-of: 2026-10-23[^c2-1][^c2-6][^c2-13][^c2-14]

### MLX-LM native vision inputs and image-aware prompt caching

- In the built-in HTTP server's chat-template path, image content parts marked image_url, input_image, or image are accepted when the loaded model has a processor. The server fetches HTTP(S) images into data URLs, decodes RGB pixels, applies the processor to the templated message, and supplies token IDs plus image embeddings to generation. This includes the common Chat Completions image_url form, which may carry a URL or base64 image data. verified-as-of: 2026-10-23[^c3-1][^c3-2]
- Tentative: For image requests, mlx_lm.server builds a modified cache key by replacing each run of image patch-token IDs with a negative ID derived from SHA-256 of the URI string passed to _make_vision. The HTTP handler first rewrites remote URLs as data URLs, so the hash input for remote images is the normalized data URI rather than the remote host path. The server performs image decoding and processor work before looking up the nearest cached prefix; after a hit, it calls model.embed_inputs only for images whose patch starts fall after the cached prefix. Thus this path can reuse KV and visual embedding work for cached image blocks, while still repeating earlier image input preparation on later requests. verified-as-of: 2026-10-23[^c3-1]
- In `mlx_lm.server` chat handling, image content is recognized on the chat-template path when a model processor is loaded; the server preserves parts with type `image_url`, `input_image`, or `image`. OpenAI's Chat Completions reference independently defines user image inputs as content-part arrays with an `image_url.url` field. verified-as-of: 2026-10-23[^c3-9][^c3-2]
- Before prompt tokenization, `mlx_lm.server` fetches HTTP(S) image URLs and rewrites them as base64 data URLs; it decodes image bytes to RGB arrays and passes those images with rendered chat text through the model processor. The OpenAI API reference documents image URLs and base64 image data as valid `image_url.url` values. verified-as-of: 2026-10-23[^c3-9][^c3-2][^c3-12]

## Methodology

- Independent MTP guidance also treats this as accepted-prefix bookkeeping: Metrale says sampler state must track accepted tokens and rejected drafts must be unwound, while an OMLX MTP discussion says a grammar matcher must advance on accepted tokens and roll back on rejected drafts.[^c1-9][^c1-8][^c1-7] _(MLX-LM stateful logits processor rollback during speculative decoding)_

## Practical Patterns

- The current mlx-lm main speculative_generate_step calls logits processors during draft and verification _step calls, then rejection cleanup truncates prev_tokens and trims model caches; the public LogitsProcessor alias is only Callable[[mx.array, mx.array], mx.array], so the interface exposes no generic processor-state rollback hook. verified-as-of: 2026-10-23[^c1-3][^c1-4][^c1-7][^c1-6] _(MLX-LM stateful logits processor rollback during speculative decoding)_
- Two remedies are described for stateful processors: recompute state from the accepted token history on each call, or add processor state snapshot and restore around speculative verification; the latter is a proposed interface need, not a generic method in the reviewed MLX-LM callable API. (two sources) verified-as-of: 2026-10-23[^c1-7][^c1-4][^c1-9] _(MLX-LM stateful logits processor rollback during speculative decoding)_
- A caller-owned LogitsProcessor becomes stateful when its object or closure mutates an FSM, grammar matcher, or counter across calls. Its callable contract takes (tokens, logits) and returns revised logits; it has no native state object or snapshot argument. Because speculative code invokes it before acceptance is known, per-call mutation can outlive a rejected candidate. (two sources) verified-as-of: 2026-10-23[^c1-10][^c1-11][^c1-7] _(MLX-LM stateful logits processor rollback during speculative decoding)_
- Tentative: In speculative_generate_step at 0d4d3d04f8ab, _draft_generate calls _step(draft_model, draft_cache, y) for each proposal. _step appends y to prev_tokens and invokes _process_and_sample(prev_tokens, logits), which applies processors in list order before logsumexp normalization and sampling. Thus processors run while proposals are being formed, not only for accepted output tokens. verified-as-of: 2026-10-23[^c1-10] _(MLX-LM stateful logits processor rollback during speculative decoding)_
- Tentative: Before main-model verification, speculative_generate_step truncates prev_tokens to remove the draft-side context extension and calls _step(model, model_cache, concatenated_input_and_drafts, num_draft+1). For n_predict>1, _step first shortens y by n_predict-1 positions; on each prediction it appends the current y to prev_tokens, calls processors with that history and logits[:, i, :], and uses the sampled main-model y for the next prediction. These are the pinned implementation inputs, not a guarantee that every processor call corresponds to an accepted token. verified-as-of: 2026-10-23[^c1-10] _(MLX-LM stateful logits processor rollback during speculative decoding)_
- Tentative: After acceptance/rejection, speculative_generate_step truncates prev_tokens by max(num_draft-n,1) positions and calls _rewind_cache(num_draft,n). That helper trims model_cache by num_draft-n and draft_cache by max(num_draft-n-1,0); finally calls it again when leaving the loop. This restores native token/cache bookkeeping but invokes no snapshot/restore callback on caller-owned processor state. verified-as-of: 2026-10-23[^c1-10] _(MLX-LM stateful logits processor rollback during speculative decoding)_
- Processor integration guidance: reconstruct derived FSM/counter state from the supplied token history on each call, including after a shorter history replaces a provisional one; do not assume calls advance an accepted prefix monotonically. A mutable external FSM needs a reset-and-replay or equivalent snapshot/rollback capability for rejected candidates, coordinated by its integration because the native callable interface supplies no such lifecycle callbacks. The upstream thinking-budget discussion explicitly contrasts stateless recomputation with a proposed save_state()/restore_state() protocol. (two sources) verified-as-of: 2026-10-23[^c1-10][^c1-7] _(MLX-LM stateful logits processor rollback during speculative decoding)_
- stream_generate enters wired_limit around generation. When maybe_set_recommended_wired_limit returns a prior limit, wired_limit synchronizes the supplied streams (or the default synchronization path) and restores that limit in finally. If the helper returns None, wired_limit yields and returns without that synchronization or restoration. Closing or exhausting an entered generator unwinds its context; LM Studio's sequential adapter explicitly closes its wrapped stream in finally. verified-as-of: 2026-10-23[^c2-1][^c2-2][^c2-13] _(MLX-LM native request cancellation and generation resource lifecycle)_
- LM Studio's adapter adds request-scoped cancellation around MLX-LM: sequential generation uses a request ID mapped to a threading.Event, checks it while waiting for the generation lock and between iterator steps, closes the underlying stream, and removes the pending-request entry; batched generation removes the matching BatchGenerator sequence and reports RequestCancelled. - Disagreement (MLX-LM stateful logits processor rollback during speculative decoding): Issue #1156 blamed stale tokens on lazy MLX array evaluation, but an MLX-LM maintainer disputed that premise; issue #1175 identified a separate MTP token-context error later addressed in PR #990.[^c1-1][^c1-2][^c1-6]
- Disagreement (MLX-LM stateful logits processor rollback during speculative decoding): An OMLX maintainer initially described generic stateful processors in its MTP loop as impractical, then reported targeted thinking-budget changes and closed the issue as completed; this limits any claim that all stateful processor support is impossible.[^c1-8]
- Disagreement (MLX-LM stateful logits processor rollback during speculative decoding): An early report attributed stale processor inputs to lazy mx.concat evaluation and proposed mx.eval as the fix. - Open (MLX-LM stateful logits processor rollback during speculative decoding): Does the targeted OMLX thinking-budget implementation generalize to custom grammar processors, or does it depend on processor-specific integration?

- Open (MLX-LM native vision inputs and image-aware prompt caching): Should the MLX-LM image identity hash use decoded pixel bytes instead of the data-URL string? The current key uses only the first 15 SHA-256 hexadecimal digits, and the source does not document collision handling or normalization for alternate encodings of identical pixels.
