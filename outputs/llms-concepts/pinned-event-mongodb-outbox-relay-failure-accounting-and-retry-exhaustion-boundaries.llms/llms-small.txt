## Problems, failure modes and limitations

- [statement] `Start` waits on cancellation, notification, polling, cleanup and stuck-recovery cases; it does not invoke the publish closure immediately on entry. MongoStore `Notifications` returns nil, so its notification case cannot trigger publishing. A store implementing `StuckRecoverer` is swept once at startup. - [statement] WithMaxRetries records only positive option values; its comment documents 0 as unlimited. The shouldSkip predicate is `r.maxRetries > 0 && msg.RetryCount >= r.maxRetries`. Its exhausted branch calls `batch.Fail(ctx, m, errExhausted)` and skips publication; neither exhaustion itself nor an error from that Fail call increments the drain failure total. - [statement] `PublishOnce` returns a wrapped readiness error, otherwise calls `drainOnce` and returns `failed to publish %d message(s)` only when its total is positive. It can therefore return nil for a batch containing only exhausted messages, even if their Fail calls log errors, provided Close succeeds. - [statement] drainOnce passes context.WithoutCancel(ctx) to deferred Close, but publication, Ack and Fail use the original context. The Close method of mongoBatch simply returns nil; the MongoDB batch source describes its claim as already committed before ClaimPending returns. ## Comparisons and alternatives

- [statement] For a store implementing Starter, the Relay's ensureReady helper wraps setup in sync.Once, so Start and PublishOnce share one store EnsureReady attempt. The readyErr field retains the first setup result; an initial setup error is returned on later calls instead of another setup attempt. The EnsureReady method of MongoStore delegates to EnsureIndexes, and both relay entry points return a readiness error before claiming a batch. (high confidence) — https://raw.githubusercontent.com/rbaliyan/event/b112463682d44b0e57d8545e3cdf5d51e112e914/outbox/relay.go · keywords: Pinned event-mongodb outbox relay failure accounting and retry exhaustion boundaries · also: https://raw.githubusercontent.com/rbaliyan/event-mongodb/ca444aedec31e7e959c0932a8f7577c15312f37e/outbox/mongodb.go
- [statement] NewRelay copies configured retryBackoff and pollDelay values into the Relay fields. Start uses those stored settings while consuming drainOnce counts rather than returning each drain error. With retryBackoff configured, positive failures increment consecutiveFailures and reset the polling ticker through NextDelay(consecutiveFailures); a subsequent zero-failure drain resets it to the stored pollDelay. Both ticker and notification wakeups invoke the same publish closure; cancellation returns ctx.Err(). (low confidence) — https://raw.githubusercontent.com/rbaliyan/event/b112463682d44b0e57d8545e3cdf5d51e112e914/outbox/relay.go
- [statement] In drainOnce, ClaimPending failure returns a count of 1. After a successful claim, a transport publish error adds one failure and calls Fail; an error from that Fail call is logged without adding another failure. An Ack error after successful publication adds one failure without calling Fail. The deferred Close adds one further failure if it errors, including for an empty batch. These counts include batch operations, rather than only distinct unsuccessfully published messages. (high confidence) — https://raw.githubusercontent.com/rbaliyan/event/b112463682d44b0e57d8545e3cdf5d51e112e914/outbox/relay.go · keywords: Pinned event-mongodb outbox relay failure accounting and retry exhaustion boundaries · also: https://raw.githubusercontent.com/rbaliyan/event/b112463682d44b0e57d8545e3cdf5d51e112e914/outbox/relay_engine_test.go, https://raw.githubusercontent.com/rbaliyan/event/b112463682d44b0e57d8545e3cdf5d51e112e914/outbox/outbox.go
- [statement] The WithMaxRetries documentation says exhausted messages remain StatusFailed and are no longer retried. NewRelay initializes the Relay's maxRetries field from the selected option before shouldSkip uses that stored field as a positive threshold against RetryCount. The exhausted branch calls ordinary Fail with errExhausted, then continues. The Fail method of mongoBatch sets StatusFailed and increments retry_count, while MongoStore's claimBatch selects pending and failed records without a retry-count ceiling. If that MongoDB Fail update succeeds, the record returns to a failed state eligible for another claim rather than a terminal excluded state. The exhausted relay branch itself skips transport publishing when its observed RetryCount meets the positive threshold. (high confidence) — https://raw.githubusercontent.com/rbaliyan/event/b112463682d44b0e57d8545e3cdf5d51e112e914/outbox/relay.go · keywords: Pinned event-mongodb outbox relay failure accounting and retry exhaustion boundaries · also: https://raw.githubusercontent.com/rbaliyan/event-mongodb/ca444aedec31e7e959c0932a8f7577c15312f37e/outbox/mongodb.go
- [statement] The WithRetryBackoff comment describes skipping an individual failed message until a delay based on its retry count expires. In the pinned implementation, Start instead delays its polling ticker by consecutive failing drains, while drainOnce contains no per-message backoff check and PublishOnce directly drains. This is an attributed documentation-versus-code difference. (low confidence) — https://raw.githubusercontent.com/rbaliyan/event/b112463682d44b0e57d8545e3cdf5d51e112e914/outbox/relay.go
