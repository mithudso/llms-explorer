SET F:
F1: A checkpoint copies committed pages from the WAL file back into the main database file. A WAL database therefore has three primitive operations: read, write and checkpoint. The checkpoint's progress is the wal-index field nBackfill, the number of WAL frames already backfilled into the database. When nBackfill equals mxFrame, the whole WAL is in the database file.
F2: The auto-checkpoint threshold is a per-connection setting. Every new connection starts at 1000 pages, or at the compile-time value SQLITE_DEFAULT_WAL_AUTOCHECKPOINT. PRAGMA wal_autocheckpoint=N and sqlite3_wal_autocheckpoint(db, N) change it. A zero or negative N turns auto-checkpointing off for that connection.
F3: All automatic checkpoints are PASSIVE. The connection whose commit pushes the WAL over the threshold runs the checkpoint itself, before the commit statement returns. Most commits stay fast and the occasional commit that triggers a checkpoint is much slower. PRAGMA wal_checkpoint with no argument and sqlite3_wal_checkpoint() are also PASSIVE.
F4: SQLite checkpoints automatically in two cases: after any COMMIT that leaves the WAL at 1000 pages or more, and when the last connection to the database closes. A connection changes the 1000-page default with PRAGMA wal_autocheckpoint=N, and a build changes it with SQLITE_DEFAULT_WAL_AUTOCHECKPOINT. Every automatic checkpoint is PASSIVE. The thread that issues the triggering COMMIT runs the checkpoint, so most commits stay fast and an occasional commit is much slower.
F5: Automatic checkpoints are always PASSIVE. So is a call to sqlite3_wal_checkpoint(), or to PRAGMA wal_checkpoint with no argument. FULL, RESTART and TRUNCATE run only when the application asks for them with sqlite3_wal_checkpoint_v2() or PRAGMA wal_checkpoint(MODE).
F6: All automatic checkpoints are PASSIVE, and so are checkpoints started by sqlite3_wal_checkpoint(). A PASSIVE checkpoint copies as many frames as it can without waiting for readers or writers, never calls the busy handler, and may leave frames uncopied while readers or writers are active.
F7: An explicit checkpoint uses sqlite3_wal_checkpoint_v2() or PRAGMA wal_checkpoint(mode), and any writable connection can start one. PASSIVE checkpoints as many frames as it can without waiting for any reader or writer, never calls the busy handler, and may stop early. FULL waits (calling the busy handler) until no writer is active and all readers use the newest snapshot, then checkpoints every frame and syncs the database file. RESTART does what FULL does, then waits until all readers read only from the database file, so the next writer restarts the log at the beginning. TRUNCATE does what RESTART does, then truncates the WAL file to zero bytes just before it returns success. NOOP (added in SQLite 3.51.0, 2025-11-04) checkpoints zero frames and only returns the counters. Plain sqlite3_wal_checkpoint() and a bare PRAGMA wal_checkpoint are PASSIVE.
F8: SQLite 3.51.0 (2025-11-04) added PRAGMA wal_checkpoint=NOOP and the SQLITE_CHECKPOINT_NOOP argument to sqlite3_wal_checkpoint_v2(). NOOP checkpoints zero frames. Its only purpose is to read the log-size and checkpointed-frame counts.
F9: The C API and pragma pages say a pending FULL or RESTART checkpoint blocks new writers but lets readers continue; TRUNCATE adds only the final truncation. The WAL guide disagrees about readers (see disagreements).
F10: Every checkpoint call takes an exclusive checkpoint lock. If another connection is already checkpointing, the call returns SQLITE_BUSY at once and never calls the busy handler. FULL, RESTART and TRUNCATE also take the writer lock and use the busy handler while they wait for the writer lock and for readers. If the busy handler returns 0 first, the checkpoint continues as a PASSIVE checkpoint and the call returns SQLITE_BUSY. TRUNCATE truncates only just before a successful return, so a call that returns SQLITE_BUSY does not truncate.
F11: If wal_checkpoint(TRUNCATE), FULL or RESTART returns busy=1 or SQLITE_BUSY, the checkpoint did not finish. When the busy handler gives up, the call falls back to PASSIVE behavior. TRUNCATE cuts the file only just before a successful return, so the -wal file keeps its size. Find and end long read transactions, then retry. A forced TRUNCATE that waits on long readers can itself stall writers, as Litestream's guide warns.
F12: A manual PRAGMA wal_checkpoint(RESTART) or sqlite3_wal_checkpoint_v2() can return SQLITE_BUSY in about a microsecond even when every connection has busy_timeout=10000. In a 2021 SQLite forum case (36 connections, about 1000 writes per second), the cause was auto-checkpoints running on other connections. The checkpoint lock is exclusive and the busy handler does not apply to it. Setting PRAGMA wal_autocheckpoint=0 on every connection fixed it.
F13: Running your own checkpointer next to SQLite's automatic one invites SQLITE_BUSY. Syncthing's developers noted (forum post, 2026-02-06) that they do not disable SQLite's automatic checkpoint, so a commit at 1000 pages triggers a passive checkpoint, and because checkpoints of any kind are exclusive, 'we're blocking our own checkpointer'. They also noted that their timer-based checkpointer needs a point of 'radio silence' in database use. SQLite's C API documents the mechanism: a second checkpointer gets SQLITE_BUSY immediately, without a busy-handler retry.
F14: Mixing auto-checkpoints with an external checkpointer makes them collide. Litestream says an application checkpoint can land between Litestream's checkpoints, make Litestream miss a WAL update, and force a fresh full snapshot; it recommends PRAGMA wal_autocheckpoint = 0 for high write load. Syncthing's maintainer reports the same lock conflict from the other side: commit-triggered passive checkpoints block the application's own checkpointer.
F15: Do not turn off automatic checkpoints unless something else checkpoints reliably. SQLite's guide says nothing then prevents the WAL from growing excessively. Syncthing found that a timer-based checkpointer may never hit a moment with no active reader, and that leaving SQLite's own auto-checkpoint enabled blocked its own checkpointer because only one checkpoint can run at a time.
F16: PRAGMA wal_checkpoint returns one row of three integers. The first is 0, or 1 when a FULL, RESTART or TRUNCATE checkpoint was blocked (the equivalent C call would return SQLITE_BUSY). The second is the number of modified pages in the WAL. The third is the number of WAL pages moved back into the database. The second and third are -1 when the database has no WAL, and both are 0 after a successful TRUNCATE. By the lock rules, a gap between the second and third values means readers or writers kept part of the WAL from being backfilled. The NOOP mode returns these counters without checkpointing any frame.
F17: If zDb is NULL or empty, sqlite3_wal_checkpoint_v2 runs on every attached WAL database and leaves pnLog and pnCkpt undefined. If one database returns SQLITE_BUSY, the call still processes the rest and returns SQLITE_BUSY at the end. Any other error stops processing at once. An attached database that is not in WAL mode returns SQLITE_OK with both counters set to -1. An unknown database name returns SQLITE_ERROR.
F18: Each reader fixes an end mark: the last valid commit in the WAL when its read began. A checkpoint can run beside readers, but it must stop at the first WAL page past the end mark of any current reader, because it would otherwise overwrite database content that reader is using. The checkpoint stores how far it got in the wal-index and resumes from there on its next run. A long-running read transaction therefore blocks checkpoint progress. Syncthing's developers put it this way: 'If a transaction is open for hours, we can't remove pages written to the WAL after its start.'
F19: The WAL resets when a writer appends frames and finds that nBackfill equals mxFrame and that no reader holds WAL_READ_LOCK(1) through WAL_READ_LOCK(4). The writer then rewinds to the start of the WAL and overwrites old frames. This reset is the mechanism that keeps the WAL from growing without bound.
F20: After a checkpoint has copied the whole WAL into the database file and no reader still depends on the WAL, the next writer rewinds to the start of the WAL file and overwrites it. This reset is what bounds WAL size. If at least one reader is always active, no checkpoint can finish, the reset never happens, and the WAL file grows without bound.
F21: The WAL file restarts only when a checkpoint has copied the whole WAL into the database and synced it, and no reader is using the WAL. The next writer then rewinds to the start of the file and writes new frames over the old ones. This reset keeps the WAL from growing without bound. A write transaction in progress also blocks the reset, so one very large write transaction produces a large WAL until it commits and a checkpoint completes.
F22: A completed checkpoint does not normally make the -wal file smaller. SQLite reuses the existing file from its start because overwriting is faster than appending. The file shrinks in two cases. If PRAGMA journal_size_limit holds a limit, SQLite compares the file size to the limit at each commit and WAL reset and truncates the file down to the limit (default -1 means no limit; 0 truncates to the minimum). A successful TRUNCATE checkpoint cuts the file to zero bytes. Litestream's guide confirms that a passive restart does not shrink the physical -wal file.
F23: PRAGMA journal_size_limit=N (default -1, no limit) trims the WAL to N bytes, but a finished PASSIVE, FULL or RESTART checkpoint does not trim it. In wal.c the trim runs at the first commit after the WAL has been restarted, and it never cuts below the end of that transaction. The pragma applies to one database, so each attached database needs its own setting.
F24: journal_size_limit is not a cap on WAL growth. SQLite applies it at commit and WAL reset, so it cannot shrink a WAL that still holds frames waiting for a checkpoint. In a 2020-11 forum thread a user set journal_size_limit and still saw the WAL reach about 1.5 to 2 GB under sustained writes; Gunter Hick replied that the limit 'only applies to an empty journal file'.
F25: Firefox compiles in SQLITE_DEFAULT_JOURNAL_SIZE_LIMIT = 1572864 bytes (1.5 MiB), and its Places database uses 4 MiB, so journal and WAL files are truncated to that limit and kept instead of being deleted (Mozilla Bug 1820478). Firefox still sets wal_autocheckpoint per database. SQLite compares the WAL size with journal_size_limit at each commit and WAL reset and truncates the file if it is larger.
F26: When the last connection closes cleanly, it takes an exclusive lock, runs a final checkpoint, and deletes the -wal and -shm files. If the last process exits without closing cleanly, or the application used SQLITE_FCNTL_PERSIST_WAL, the -wal file stays on disk. With SQLITE_FCNTL_PERSIST_WAL the final checkpoint still runs.
F27: When the last connection to a WAL-mode database closes or detaches, SQLite runs one final checkpoint and deletes the WAL file. sqlite3_db_config(SQLITE_DBCONFIG_NO_CKPT_ON_CLOSE) turns off that final checkpoint: a positive value disables it, and zero (the default) enables it.
F28: When the last connection to a WAL database closes, it checkpoints and deletes the -wal and -shm files. SQLITE_DBCONFIG_NO_CKPT_ON_CLOSE turns off that checkpoint. If the last process exits without closing cleanly, or SQLITE_FCNTL_PERSIST_WAL is in use, the WAL file stays on disk. A database file separated from its WAL can lose committed transactions or become corrupt, so the WAL must travel with the database.
F29: Checkpoints perform the fsyncs that make WAL data safe. SQLite syncs the WAL before its content moves into the database, and syncs the database file before the WAL resets. With synchronous=NORMAL in WAL mode, commits do not sync. SQLite then syncs the WAL before each checkpoint, the database file after each completed checkpoint, and the WAL header when the WAL is reused after a checkpoint. A transaction committed under NORMAL can roll back after a power loss or OS crash. synchronous=FULL adds a WAL sync after every commit.
F30: Checkpoint frequency trades read speed against write speed. A reader checks the WAL for each page it needs, so read cost grows with WAL size. A checkpoint is slower than a write transaction because it syncs and seeks. Frequent checkpoints keep reads fast. Infrequent checkpoints spread each checkpoint's cost over more writes. SQLite calls its 1000-page default a setting that worked well in tests on workstations and says other platforms or workloads may need other values. Android's framework config adds that a bigger WAL makes each checkpoint take longer.
F31: Checkpoint starvation makes the WAL grow without bound. A checkpoint cannot reset the WAL while another connection holds a read transaction. If many overlapping readers keep at least one reader active at all times, no checkpoint ever completes. SQLite's remedy is reader gaps: times with no readers, when checkpoints are attempted. With many concurrent readers, SQLite also suggests manual RESTART or TRUNCATE checkpoints, which run to completion before returning, at the price that readers might block. A Syncthing maintainer summarized the effect in February 2026: the WAL grows indefinitely until a checkpoint completes, and multiple gigabytes is critical.
F32: Three setups let the WAL grow without bound. First, automatic checkpoints are disabled and nothing else checkpoints. Second, checkpoint starvation: overlapping readers mean at least one reader is always active, so no checkpoint can finish or reset the WAL. Third, a very large write transaction blocks the reset until it commits. SQLite's remedies are to leave reader gaps and checkpoint in them, and, where many readers overlap, to run manual RESTART or TRUNCATE checkpoints, accepting that readers may block. Litestream's guide adds an emergency truncate tier as a brake against runaway growth, and Syncthing's developers expect database operations to 'grind to a halt' once the WAL reaches multiple gigabytes.
F33: To bound the WAL under constant read load, SQLite's WAL guide offers two options: create reader gaps (times with no active reader) in which PASSIVE checkpoints can finish, or run RESTART or TRUNCATE checkpoints, which finish before they return but can block readers while they run. Litestream's emergency tier uses the same escalation: PASSIVE first, then a blocking TRUNCATE only if the WAL stays above its threshold.
F34: better-sqlite3 advises a watchdog for apps with concurrent readers: every 5 seconds, stat the -wal file and run wal_checkpoint(RESTART) when it exceeds a chosen size. It says an app that never accesses the database from several processes or threads at once never meets starvation. SQLite's own docs recommend RESTART or TRUNCATE for the same case.
F35: Starvation needs no single long transaction. In Syncthing's analysis (issue 10559, opened 2026-02-04), pages were still moving from the WAL to the database, but many short reads arrived in quick succession and the timer-based application checkpointer never found a moment with no active reader.
F36: A very large write transaction can create a very large WAL. A checkpoint cannot reset the WAL in the middle of a write transaction, so the file can grow until the transaction ends and no reader blocks the checkpoint. Since SQLite 3.11.0 (2016-02-15) the WAL for a single transaction is proportional to the transaction's size; older versions could write the same page into the WAL several times once the transaction outgrew the page cache.
F37: A large write transaction can push the WAL well past the autocheckpoint threshold, because SQLite checks the threshold only after a commit. Forum contributors name large write transactions as a reason checkpoints cannot keep the WAL small, and one says the WAL size is roughly bounded by the autocheckpoint size plus the largest transaction.
F38: VACUUM in WAL mode writes the whole rebuilt database into the WAL as one transaction, and SQLite cannot reset the WAL in the middle of a transaction, so the -wal file stays large afterwards. Run PRAGMA wal_checkpoint(TRUNCATE) after the VACUUM to give the space back.
F39: SQLite documents application-controlled checkpointing: disable the automatic checkpoint, then run checkpoints at idle moments, in a separate thread, or in a separate process. With synchronous=NORMAL, the main thread then never blocks on a sync, which avoids 'latch-up' on a busy disk. The cost is durability: a committed transaction can roll back after a power failure.
F40: To keep checkpoint cost off the commit path, an application can set wal_autocheckpoint to 0 (or install its own wal_hook) and run checkpoints from another thread or process during idle moments. With synchronous=NORMAL the main thread then never waits on fsync, at the price of durability after a power loss. dqlite works this way: it disables automatic checkpoints, blocks user-initiated ones, and runs its own stop-the-world TRUNCATE checkpoint. Litestream also runs the checkpoints itself. The application then owns the job of keeping the WAL bounded.
F41: sqlite3_wal_autocheckpoint() is a wrapper around sqlite3_wal_hook(). A connection has one WAL hook. Registering a custom hook disables the auto-checkpoint, and calling sqlite3_wal_autocheckpoint() replaces any custom hook. A custom hook runs after each commit to the WAL and can call sqlite3_wal_checkpoint() or sqlite3_wal_checkpoint_v2() on its own criteria.
F42: sqlite3_wal_hook() registers one callback per connection. SQLite calls it after each commit, once the write lock is released, with the database name and the number of pages now in the WAL. Registering a hook replaces the built-in autocheckpoint; calling sqlite3_wal_autocheckpoint() or PRAGMA wal_autocheckpoint replaces any hook; a threshold of zero or less, or a NULL hook, turns automatic checkpointing off. With a custom hook the application must call sqlite3_wal_checkpoint_v2() or PRAGMA wal_checkpoint periodically so the WAL does not grow without bound.
F43: The automatic-checkpoint hook fires only on a connection whose own commit wrote WAL frames. In wal.c, sqlite3WalFrames sets iCallback only when it writes a commit, and sqlite3WalCallback returns 0 if this connection has committed nothing since its last call. In vdbeapi.c, doWalCallbacks calls the hook only when that value is above 0. A connection that only reads therefore never starts an automatic checkpoint.
F44: Litestream v0.5.x runs three checkpoint tiers after each sync and checks the emergency tier first. The page-count tier runs a PASSIVE checkpoint when the WAL exceeds min-checkpoint-page-count, default 1000 pages (about 4 MB). The time tier runs a PASSIVE checkpoint every checkpoint-interval, default 1 minute, if the WAL has at least 1 page. The emergency tier, truncate-page-n, defaults to 121359 pages (about 500 MB). Since v0.5.15 it tries PASSIVE first and forces TRUNCATE only if the WAL stays above the threshold. Setting checkpoint-interval or truncate-page-n to 0 disables that tier. min-checkpoint-page-count cannot be 0.
F45: A forced Litestream TRUNCATE inherits RESTART semantics: it waits for active readers and writers, and it blocks writers while it waits. A long-lived reader therefore causes write timeouts and 'database is locked' errors. The log line 'forcing truncate checkpoint' marks a blocking checkpoint. The line 'wal restarted by passive checkpoint, skipping truncate checkpoint' means the passive attempt avoided one. For apps with long-lived readers, Litestream suggests truncate-page-n: 0 plus monitoring of the -wal size, which accepts unbounded WAL growth.
F46: Litestream keeps a long-running read transaction open so that no other process can checkpoint and restart the WAL. It reads new WAL pages continuously and calls SQLite itself to checkpoint when needed. A contributor in a 2023 issue confirms the read transaction is deliberate: it prevents application checkpoints.
F47: If an application checkpoint wins the race against Litestream, a December 2023 Litestream issue says Litestream forces a new generation and takes a full snapshot to stay consistent. The issue page names no Litestream version, so this may describe the v0.3 generation model rather than v0.5.
F48: For high write loads, Litestream's tips page recommends PRAGMA wal_autocheckpoint = 0, because an application checkpoint between Litestream's checkpoints can make Litestream miss a WAL update; when it detects this it takes a fresh full snapshot. The page says checkpoint detection improvements in v0.5.0 and later reduce the need for snapshots. In issue 547 (opened 2023-12-19), hifi tested removing Litestream's read lock and found that recovery still worked, with the remote never corrupted.
F49: Litestream's tips page says it needs periodic but short write locks while it checkpoints, and recommends PRAGMA busy_timeout = 5000 (5 seconds) in the application.
F50: To see whether checkpoints keep up, compare the log and checkpointed counts that PRAGMA wal_checkpoint returns. PRAGMA wal_checkpoint(NOOP), available from SQLite 3.51.0, reads both counts without copying any frame. A PASSIVE checkpoint can leave frames behind when readers or writers are active, so a gap that persists across PASSIVE runs is consistent with a long-lived reader. Litestream's troubleshooting steps run PRAGMA wal_checkpoint(PASSIVE) for this diagnosis and watch the -wal file size, which is a high-water mark and does not shrink after a normal checkpoint.
F51: To find out why a WAL will not shrink, force a checkpoint and read the result row. busy=1 means a blocker stopped a RESTART, FULL or TRUNCATE checkpoint; log larger than checkpointed means frames are still waiting. In a SQLite forum thread (2020-11-11), Simon Slavin advised that if a forced checkpoint does not shrink the WAL, 'something is preventing checkpointing', probably a statement that was never finalized or reset.
F52: The 1000-page threshold counts pages, not bytes. SQLite's docs equate 1000 pages with about 4 MB, which assumes 4096-byte pages. The default page size was almost always 1024 bytes before SQLite 3.12.0 (2016-03-29) and is 4096 bytes since, so a database created with 1024-byte pages reaches 1000 pages at roughly 1 MB. A database cannot change its page_size after it enters WAL mode.
F53: Turning off automatic checkpoints, or installing a WAL hook that never checkpoints, without a replacement checkpointer lets the WAL grow without bound. Litestream issue 547 notes that an application which disables autocheckpoint for Litestream's sake leaves users who do not run Litestream with 'an endlessly growing WAL'.
F54: In the Syncthing thread of 2026-02-06, the maintainer named three causes that keep checkpoints from truncating a growing WAL: transactions open for hours, such as vacuum; no quiet window for a timer-based application checkpointer, because the database is read and written almost constantly while a large folder is processed; and auto-checkpoints left on, so commits run passive checkpoints that block the application's own exclusive checkpointer. The maintainer also floated running the checkpoint heuristic when a connection returns to the pool.
F55: Syncthing developers (forum thread of 2026-02-06) found the WAL can reach multiple gigabytes when long transactions pin pages and their timer-based checkpointer finds no quiet window. They proposed moving the checkpoint heuristic into the connection pool, so releasing a connection can trigger a checkpoint, and allowing WAL truncation with exclusive locking once the WAL is critically large. Both were proposals, not shipped changes.
F56: Do not hold a read transaction open across slow work. Syncthing's maintainer wrote that if a transaction is open for hours, SQLite cannot remove pages written to the WAL after the transaction started, and the WAL 'will grow indefinitely until we're able to complete a checkpoint'. Litestream's guide warns that long-lived read transactions cause extended blocking when it forces a TRUNCATE.
F57: Statements that are never reset or finalized can hold transactions open and block checkpoints. Richard Hipp wrote (2021-04-06) that with unreset write statements 'you will likely be leaving some transactions open, which will prevent the checkpoint from happening'. In a 2020-11 thread, Simon Slavin pointed to a step() that was never finalized or reset, and Gunter Hick listed open read transactions, large write transactions and disabled checkpointing as reasons a checkpoint cannot finish.
F58: Do not separate a WAL-mode database from its -wal file. If the .db file is copied or moved without its -wal file, committed transactions can be lost and the database can become corrupt. The only safe way to remove a leftover -wal file is to open the database with a sqlite3_open() interface and close it with sqlite3_close(). Litestream's tips describe the hazard from the other side: if you delete the .db but leave the -wal, SQLite applies the old WAL pages to the new database.
F59: The wal-index (-shm file) needs more than one hash table only when the WAL exceeds 4079 frames. The default threshold of 1000 pages rarely reaches that size, so a higher wal_autocheckpoint value lets the shm file grow beyond one hash table once the WAL passes 4079 frames.
F60: Checkpoint progress (nBackfill) lives in the wal-index shared memory. SQLite never syncs the wal-index and deletes its file when the last connection closes. Crash recovery rebuilds the wal-index by scanning the WAL and sets nBackfill to zero, so the next checkpoint treats no frame as backfilled.
F61: Production embedders set their own WAL limits instead of relying on SQLite's defaults. Android's framework config (main branch) sets db_wal_autocheckpoint to 100 pages, db_journal_size_limit to 524288 bytes and db_wal_sync_mode to NORMAL. A 2023 Firefox commit (Bug 1820478, 2023-05-12) builds its bundled SQLite with SQLITE_DEFAULT_JOURNAL_SIZE_LIMIT=1572864 bytes (the Places database uses 4 MiB) and, in early-beta-or-earlier builds, persists the -wal and -shm files, relying on the size limit so the WAL is truncated rather than deleted at shutdown.
F62: The WAL-reset bug is a data race between a checkpoint and a commit that resets the WAL, and it can corrupt a WAL-mode database. SQLite developer Dan found and fixed it on 2026-03-03. It is likely present in every release from 3.7.0 (2010-07-21) through 3.51.2 (2026-01-09). It is fixed in 3.51.3 (2026-03-13) and later, with backports in 3.44.6 and 3.50.7. It needs WAL mode, two or more connections on the same file in separate threads or processes, and a write and a checkpoint at the same instant. SQLite advises upgrading but says this is 'not an emergency'.
F63: WAL-reset bug: in WAL mode, a data race between a checkpoint and a write transaction can make a later checkpoint skip parts of a committed transaction, so those pages never reach the database file and the file goes corrupt. It needs two or more connections (separate threads or processes) that write or checkpoint at the same instant. SQLite's WAL page says it is likely present in every release from 3.7.0 (2010-07-21) through 3.51.2 (2026-01-09) and is fixed in 3.51.3 (2026-03-13) and later. The 3.53.0 notes (2026-04-09) list the fix too. Release 3.52.0 (2026-03-06) is marked withdrawn, with its features moved to 3.53.0. The newest release on the change log at verification was 3.54.1 (2026-10-16).
F64: SQLite's WAL page names backports of the WAL-reset fix for older branches: 3.44.6 and 3.50.7. The SQLite release history page does not list those two versions, so only the WAL page supports them.
F65: The WAL-reset bug needs a WAL-mode database with two or more connections open in separate threads or processes that write or checkpoint at the same instant. The sequence: a first checkpoint completes fully; a second checkpoint starts; while it starts, another connection commits a transaction that resets the WAL and writes new frames at its beginning; the second checkpoint misses the reset because of a data race and leaves a wal-index header field claiming frames are already checkpointed; later commits grow the WAL past its earlier length; a third checkpoint then skips part of the transaction written after the reset, so those pages never reach the database file.
F66: Mechanism of the WAL-reset bug: a first checkpoint copies the whole WAL; a second checkpoint starts and reads the wal-index header; a commit on another connection resets the WAL and writes new frames at its start; the second checkpoint does not notice the reset and leaves nBackfill claiming frames are backfilled that are not; after more commits a later checkpoint skips part of the post-reset transaction, so those pages never reach the database file. In Phil Eaton's trace the checkpointer reads mxFrame=360, the writer resets mxFrame to 0, bumps the salt, sets nBackfill=0 and commits 5 frames, then the checkpointer sets nBackfill=360. The fix compares the live WAL salt with the salt read at checkpoint start and skips the checkpoint if the WAL was reset. Canonical calls it a single extra check.
F67: In Eaton's trace of the race, the checkpointer reads the wal-index header (mxFrame=360). A writer then runs walRestartHdr (mxFrame=0, salt incremented, nBackfill=0, read marks cleared) and commits 5 new frames. The checkpointer's stale check nBackfill < mxFrame still passes, so it sets nBackfill=360, and the next checkpoint starts at frame 361 and skips frames 1 to 5, which hold live data. A large database with a large mmap_size widens the window because wal.c unmaps the database file inside it. ThreadSanitizer on 3.51.2 flagged the read of nBackfill in walCheckpoint against the atomic store in walRestartHdr.
F68: SQLite 3.52.0 (2026-03-06) included the WAL-reset fix but was withdrawn because some new features were not fully compatible with prior releases. SQLite released 3.51.3 (2026-03-13) in its place with the WAL-reset fix and minor fixes. 3.53.0 (2026-04-09) re-released 3.52.0 with extra changes for stale expression indexes and is the first major release that contains the fix.
F69: SQLite 3.52.0 (2026-03-06) is marked withdrawn on SQLite's release page, and its planned features moved to 3.53.0. SQLite 3.51.3 (2026-03-13) lists one WAL change: 'Fix the WAL-reset database corruption bug.' SET H:
H1 (run 1): A checkpoint copies committed WAL frames into the main database file. When several frames hold versions of the same page, only the newest version is written; superseded versions are skipped.
H2 (run 1): A checkpoint runs concurrently with readers but must stop at the first WAL frame past the end mark of any active reader, because copying it would overwrite database pages that reader is still using. The checkpointer records its progress in the wal-index and resumes from that point on the next call, so a read transaction that stays open for hours pins every WAL page written after it started.
H3 (run 1): The WAL is reset, not truncated, by default: once every frame has been checkpointed and synced and no reader is still using the WAL, the next writer rewinds to the start of the file and overwrites old frames. A new salt in the WAL header makes stale frames with the old salt invalid, and the header's checkpoint sequence number increments. The -wal file only shrinks when journal_size_limit is set or a TRUNCATE checkpoint runs.
H4 (run 1): Automatic checkpoints are PASSIVE and run inside the committing connection, in the committing thread, when a COMMIT leaves the WAL at or above wal_autocheckpoint pages. The default is 1000 pages (compile-time SQLITE_DEFAULT_WAL_AUTOCHECKPOINT), roughly 4 MB at the default 4096-byte page size. The setting is per connection; zero or a negative value disables it for that connection only.
H5 (run 1): When the last connection to a WAL-mode database closes, SQLite runs a final checkpoint and then deletes the -wal and -shm files. With auto-checkpoint disabled, nothing else bounds WAL growth.
H6 (run 1): sqlite3_wal_checkpoint_v2() and PRAGMA wal_checkpoint accept five modes. PASSIVE copies as many frames as it can without waiting and never calls the busy handler. FULL waits for the current writer to finish and for all readers to reach the latest snapshot, then copies every frame and syncs the database. RESTART does FULL and then waits until no reader uses the WAL, so the next writer restarts the log from the beginning. TRUNCATE does RESTART and then truncates the -wal file to zero bytes. NOOP, added in SQLite 3.51.0, checkpoints nothing and only reports the frame counts.
H7 (run 1): FULL, RESTART and TRUNCATE take the exclusive writer lock and invoke the busy handler while waiting for the lock and for readers. They block new writers while pending but let new readers proceed unimpeded. If the busy handler gives up, the call completes what it can like PASSIVE and returns SQLITE_BUSY; the pragma reports this as busy=1 in its first column.
H8 (run 1): Every checkpoint call first takes an exclusive checkpoint lock. If another connection or process already holds it, the call returns SQLITE_BUSY at once without invoking the busy handler. Checkpoints are therefore mutually exclusive, and a 1000-page auto-checkpoint from any connection can make an application's own RESTART or TRUNCATE checkpoint fail with SQLITE_BUSY.
H9 (run 1): PRAGMA wal_checkpoint returns one row with three columns: busy (0, or 1 if a FULL, RESTART or TRUNCATE checkpoint was blocked), log (frames in the WAL) and checkpointed (frames moved into the database so far). If the database is not in WAL mode the last two columns are -1 and the pragma is a no-op. After a successful TRUNCATE both counts are 0. Ignoring the busy column hides failed checkpoints, which Syncthing found it had been doing.
H10 (run 1): With PRAGMA synchronous=NORMAL in WAL mode the checkpoint is the only sync point: the WAL is fsynced before each checkpoint, the database file after each completed checkpoint, and the WAL header when the file is reused, while ordinary commits do no fsync. synchronous=FULL adds a WAL fsync after every commit; EXTRA is identical to FULL in WAL mode. Litestream recommends NORMAL for this reason.
H11 (run 1): Checkpoints cost more than write transactions because they fsync and seek, and read performance falls as the WAL grows because readers must search it. Frequent checkpoints favour reads; infrequent ones favour writes. Because the committing thread runs auto-checkpoints, most commits are fast but some stall on the checkpoint; running checkpoints from a dedicated thread, process or service keeps commits from blocking on fsync.
H12 (run 1): Checkpoint starvation: if overlapping read transactions ensure there is always at least one active reader, no checkpoint can run to completion and reset the WAL, and the -wal file grows without bound (PASSIVE auto-checkpoints never force the issue). Mitigations are to create reader gaps, keep read transactions short, or issue RESTART or TRUNCATE checkpoints, which wait for readers but can stall writers.
H13 (run 1): A single prepared SELECT that has been stepped to a row but not stepped to SQLITE_DONE or passed to sqlite3_reset() keeps its read transaction open and alone pins the WAL end mark, so the WAL grows past the 1000-page auto-checkpoint threshold even with one connection. A forum reproducer showed this on SQLite 3.30.0 and 3.38.5; resetting or finishing the statement promptly kept the WAL near 4 MB.
H14 (run 1): A checkpoint cannot reset the WAL in the middle of a write transaction, so one large transaction produces a WAL at least as large as the transaction. VACUUM in WAL mode writes the whole rebuilt database into the WAL, nearly doubling disk use until a checkpoint runs. Since SQLite 3.11.0 (2016-02-15) a transaction's WAL footprint is proportional to its size; earlier versions could write the same page more than once.
H15 (run 1): After VACUUM in WAL mode, run PRAGMA wal_checkpoint(TRUNCATE) to move the rebuilt pages into the database and shrink the -wal file; otherwise the space has only moved from the database to the WAL. journal_size_limit does not limit WAL growth during the VACUUM transaction, only after a checkpoint or reset.
H16 (run 1): PRAGMA journal_size_limit (default -1, no limit) truncates the -wal file down to the limit each time a transaction commits or the WAL resets; 0 always truncates to the minimum. It applies to one database on one connection, so with a connection pool it must be set on the connection that performs the checkpoint. Syncthing saw TRUNCATE shrink the WAL to zero bytes despite journal_size_limit=67108864 because the pragma had been set on a different pooled connection.
H17 (run 1): sqlite3_wal_hook() registers a callback invoked after each WAL-mode commit with the connection, the database name and the current number of WAL pages; the callback may read, write or checkpoint, and a non-SQLITE_OK return propagates to the caller although the commit has already happened. Auto-checkpoint (the C function and the pragma) is built on this hook and overwrites any earlier hook; registering your own hook, or passing NULL, replaces auto-checkpoint. This is the intended way to implement custom checkpoint policy.
H18 (run 1): Passing NULL or an empty string as zDb to sqlite3_wal_checkpoint_v2() checkpoints every attached WAL database; pnLog and pnCkpt are then undefined, SQLITE_BUSY on one database does not stop the others, and SQLITE_BUSY is returned at the end. Naming a non-WAL database returns SQLITE_OK with both counts -1; naming an unknown database returns SQLITE_ERROR.
H19 (run 1): Litestream holds a long-running read transaction between its own checkpoints so no other process can checkpoint and restart the WAL before it has copied the frames. Under heavy write load (tens of thousands of small writes per second) an application auto-checkpoint can still slip in, after which Litestream takes a fresh full snapshot; it therefore recommends PRAGMA wal_autocheckpoint=0 plus PRAGMA busy_timeout=5000 in the application. v0.5.0+ improved checkpoint detection reduces the snapshot fallback.
H20 (run 1): Litestream v0.5.x uses a tiered policy: a PASSIVE checkpoint when the WAL exceeds min-checkpoint-page-count (default 1000 pages, about 4 MB) or every checkpoint-interval (default 1m), and an emergency checkpoint when the WAL exceeds truncate-page-n (default 121359 pages, about 500 MB) that tries PASSIVE first and forces TRUNCATE only if the WAL stays above the threshold (passive-first since v0.5.15). A forced TRUNCATE waits for all readers and writers and takes a boundary snapshot under the write lock, so it can stall writers; truncate-page-n=0 avoids blocking but leaves WAL size unbounded.
H21 (run 1): Syncthing's SQLite backend ran PRAGMA wal_checkpoint(TRUNCATE) every 8 hours with a 64 MiB journal_size_limit while leaving SQLite auto-checkpoints enabled and ignoring the busy column. It hit multi-gigabyte WAL files, diagnosed three causes (hours-long read transactions, near-constant activity leaving no idle window for RESTART or TRUNCATE, and auto-checkpoints colliding with its own checkpointer), and proposed disabling auto-checkpoint, a dedicated checkpointer triggered by WAL size or connection release, and shorter read transactions.
H22 (run 1): Splitting long read work into short read transactions and issuing PRAGMA wal_checkpoint(RESTART) when starvation is detected cut Syncthing's WAL on a 2.5 GB database from about 2.2 GB to about 128 MiB during index resets (Syncthing PR #10027).
H23 (run 1): The WAL-reset bug is a data race between a checkpoint and a write transaction that resets the WAL, when two or more connections (separate threads or processes) write or checkpoint at the same instant. The second checkpoint misses the reset and leaves the wal-index backfill count (nBackfill) wrong, so a later checkpoint skips part of a committed transaction: committed pages are never written to the database while pages that reference them are, producing lost writes and a corrupt file. SQLite says it is likely present from 3.7.0 (2010-07-21) through 3.51.2 (2026-01-09); it is fixed in 3.51.3 (2026-03-13) with backports in 3.44.6 and 3.50.7. 3.52.0 also carried the fix but was withdrawn for an unrelated regression.
H24 (run 1): SQLite describes the WAL-reset race as unlikely in common use and says its developers never reproduced it organically, only with a test hook. Tailscale nevertheless recorded 19 corruption incidents over about six months from August 2025 with a single Go process per shard that checkpoints manually and very aggressively, and Antithesis reproduced it on 3.51.2 in about 15 minutes with a generic workload of concurrent writes and checkpoints; the same workload ran clean on 3.51.3. Tailscale had run four months without incidents as of August 2026.
H25 (run 1): The 3.51.3 fix is a single extra check: the checkpointer confirms, by comparing the WAL salt, that the WAL was not reset since the checkpoint began. Canonical's TLA+ model found the corrupting trace in about 20 states; dqlite is unaffected because it blocks user-initiated checkpoints, disables automatic ones and runs its own checkpoint as a stop-the-world action under the write lock, so a writer and a checkpoint can never overlap.
H26 (run 1): Practical hardening for applications that drive checkpoints themselves: upgrade to SQLite 3.51.3 or later; disable auto-checkpoint on every connection if one component owns checkpointing; always check the busy column or SQLITE_BUSY return and retry; run PRAGMA integrity_check on backups continuously; and treat non-standard, aggressive checkpoint schedules as a risk surface, since that is where the WAL-reset race surfaced in production.
