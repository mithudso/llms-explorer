### 1. Continuation recovery

**Trigger:** “resume,” “retry,” “finish the previous run,” or a handoff that names already-completed work.

Read the scoped prompt and memory, graph task, Git state and canonical runner ledger. Resolve the active checkout and distinguish accepted, rejected, pending and superseded artifacts. Preserve frozen inputs and accepted gates. Return a small resume plan containing the exact next command, source revision, remaining steps and any genuine blocker. Invoke the workflow's own resume interface when authorized; never reconstruct its helper-owned state by hand.

**Evidence:** the optimizer continuation ends in a precise publication state [E1]. The local-model review explicitly prohibits replaying accepted gates [E2]. The repository handoff still requests work on an older branch name [E3]. These are different forms of continuation ambiguity.

**Overlap:** `project-registrar` locates projects and activation commands. `convergence-loop-runner` owns optimizer iterations. This agent should recover their continuation context and hand it back, rather than implement another registry or optimizer.

**Acceptance example:** give it a completed CPU gate plus a pending physical gate. It identifies the physical next step without rerunning or editing the accepted CPU artifact.

### 2. Live acceptance verifier

**Trigger:** “I still see the old behavior,” “fix what is actually loaded,” or completion of a browser, TUI, extension or launch-agent change.

Trace the executable, process, installation path, revision and relevant runtime configuration. Exercise the actual user action and save console/process evidence or screenshots where useful. Report source validation, installed revision and observed behavior separately. A simulation or passing unit suite must not stand in for the loaded application.

**Evidence:** GitHub Explorer's release record separately verifies the installed registry package and deployed browser pages [E4]. Net-DNS-Monitor's memory records live launch-service state in addition to automated checks [E5]. Skills Explorer records installed-package smoke checks [E6].

**Overlap:** browser/debugging skills, `repo-bootstrapper`, platform publishing and `project-registrar` already supply pieces. The gap is a common loaded-state trace and acceptance receipt across those surfaces.

**Acceptance example:** a new source revision exists while an older binary runs. It reports the mismatch and cannot mark acceptance complete.

### 3. Local model qualification

**Trigger:** a proposed runtime, quantization, gateway, context size, speculative decoder or hardware promotion.

Load the original qualification contract. Bind actual model bytes, executable/build provenance, template, tokenizer, full agent payload, tool schema and hardware session. Keep cold/warm and cached/uncached measurements separate. Require the original numerical gates, genuine coding tools and standard research workflow where specified. Save a typed result that states exactly which gates passed and what remains unqualified. Failed gates remain failed unless the user changes the contract.

**Evidence:** the focused Mac review preserves original memory and numerical limits and warns that source inspection does not prove compiled behavior [E2]. The existing Mac expert skill already covers runtimes, caches, agent compatibility and quantization [E7]. The graph's exact-payload decision, KNOW-530, says proxy token estimates are not actual model-token or physical GPU measurements.

**Overlap:** reuse the Mac expert corpus, model-layer hub and existing qualification runners. The valuable addition is a disciplined operator and independent result audit, not another general local-LLM survey.

**Acceptance example:** the server answers a greeting but fails numerical or full-tool admission. The receipt says smoke success and qualification failure.

### 4. Research contract auditor

**Trigger:** “verify this research,” “submit through this typed interface,” or “finish the reviewed run.”

Read the exact run contract and canonical helper outputs. Check fetched text, nonempty read-to-source bindings, independent organizations, negation evidence, claim scope, source dates and telemetry. Distinguish inherited parent evidence from child-specific proof. Verify publication through the required interface and its read-back receipt. Mechanical checks belong in scripts; the agent should judge source relevance and unsupported inference. It should not rewrite accepted manifests to make a gate pass.

**Evidence:** the frontier continuation distinguishes evidence-only deltas from fully qualified research and leaves independent-origin verification pending [E8]. A Claude memory shows that prose self-grading reported eight successes while a mechanical check found only two [E9]. Another memory warns that an unfinished background search is not an empty result [E10].

**Overlap:** `/dr`, claim-verdict helpers, typed publication tooling and existing document validators already cover portions. Add a reusable contract adapter and independent audit; do not create a second research engine.

**Acceptance example:** a URL is cached but no readable passage is bound to the claim. The auditor reports an evidence gap even if the file exists and JSON parses.

### 5. Memory health and handoff reconciliation

**Trigger:** repeated stale handoff injection, oversized memory, conflicting “done” and “remaining” records, or periodic memory maintenance.

Extend the existing memory compiler and remember maintenance workflow. Measure injection size and age. Resolve path aliases before calling a source stale. Compare completion statements against canonical task/release receipts, identify duplicate versions and propose supersession links. Preserve provenance and paused/open work. Produce a bounded current handoff plus a reversible cleanup proposal; automatic cleanup needs an explicit maintenance invocation and clear ownership.

**Evidence:** the repository handoff retains an older provider task and publication instruction [E3]. The memory-pyramid project already has stable IDs, reconciliation, deduplication and provenance facilities [E11]. The hub memory's upper and lower entries represent different dates and unresolved states [E12].

**Overlap:** `/mcl`, remember maintenance, NapMem, Stele and `project-registrar` already exist. Extend them first. A wrapper agent is useful only if it coordinates cross-store reconciliation that these tools do not already perform.

**Acceptance example:** archive a repeated completed handoff only after finding the canonical completion receipt. Retain a separate paused research run and its exact resume pointer.

### 6. Agent asset parity auditor

**Trigger:** “the rule was ignored,” “the skill disappeared,” “sync brought it back,” or a migration/configuration change.

Build a provenance map from canonical source to hub reference, migrated asset, routing index and actual harness discovery. Compare content hashes, versions, enabled state and source pins. Identify concurrent writers, mirror direction and folded-skill resurrection. Probe tool/skill discovery without executing inference or rebuilding indexes. Default to read-only; repair only the selected assets through their canonical synchronization tool.

**Evidence:** the configuration memory documents a missing guidance import and a focused hash-backed repair [E13]. The hub record describes missing router tool rows and stale refresh wiring as of its recorded date [E12]. Claude project memories record scheduler collisions, unpinned pruning and async hooks reverting newer frontmatter [E14, E15]. Consolidation records also describe sync resurrecting folded standalones [E16].

**Overlap:** `box-sync`, skill meta-validation, `skill-tree-architect` and configuration migration are existing execution tools. Add verification across the complete source-to-loaded chain, rather than another sync implementation.

**Acceptance example:** a source skill exists but is absent from active discovery. The audit reports its availability and the broken transition instead of claiming installation success.

### 7. Distribution release closer

**Trigger:** “publish,” “ship,” “merge/push,” or completion of a package release that also has website promotion.

Track one version through source, built artifact, registry, release downloads, installation and website. Use channel-specific existing tooling, CI and checksums. Preserve unrelated worktrees and draft work. Verify a fresh install and final public behavior. Keep a release receipt with separate states for Git merge, artifact publication, promotion and acceptance.

**Evidence:** the GitHub Explorer release required registry authentication, artifact hashes, fresh installation and website deployment checks [E4]. The Skills Explorer record combines source publication and installed acceptance [E6].

**Overlap:** `repo-hygiene-agent` handles Git hygiene; CI/CD and Apple publishing skills handle their channels. This agent should coordinate release acceptance without broadening repo hygiene into unrequested package publication.

**Acceptance example:** a PR is merged but the registry still serves the previous version. The release remains incomplete and names the missing publication step.

## Focused skill additions

Three smaller additions would make the agents more reliable. Place them behind existing hubs unless observed usage justifies a standalone skill.

1. **Textual job and process lifecycle reference** under the Python/frontend tooling: background job screens, stream terminal states, cancellation, stderr capture, installed executable checks and filesystem watcher teardown. Explorer memory describes a silent headless subprocess suspending the TUI [E17]. This is narrower than general Python testing.
2. **Guarded artifact writes reference and helper** under agent/MCP orchestration: fresh hashes, compare-and-write, owned paths, concurrent-writer detection, read-back and retry without stale IDs. The actual trigger cases are frontmatter rollback and overlapping scheduled/manual writers [E14, E15]. Reuse existing guarded-write helpers before adding one.
3. **Userscript interaction invariants reference** under the extension/browser hub: confirmed private composer, draft without sending, preserve user text, selection after script fill and modifier-click behavior. The greeting prompt provides a concrete positive requirement [E18]. These behaviors should be explicit acceptance fixtures for userscript changes.

Also extend `skill-gap-filler` with this audit method: mine workflow records, normalize duplicated sessions/worktrees, compare loaded capabilities, rank marginal value, and provide a recommendation-only mode. Its current definition emphasizes domain research and skill creation; this request benefits from evidence mining before creation.

## Implementation order

Start with continuation recovery and live acceptance. Reuse their source/loaded-state receipts in model qualification. Add the research auditor's contract adapters next. Extend memory maintenance and asset-parity verification before scheduling either automatically. Add release closure once a shared release receipt exists.

Each new capability needs one named owner, a bounded trigger, canonical helper calls, a small machine-readable output and adversarial acceptance fixtures. Include near-miss cases that must route to an existing skill. Do not build all recommendations as standalone skills simply because they appear in this report.
