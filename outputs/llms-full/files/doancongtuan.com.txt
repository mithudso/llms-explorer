## Editorial principles

The site should be interpreted with these editorial rules:

1. Experience level matters.
   - Hands-on: used in real projects or production-like work.
   - Hands-on, cautious: real use, but context or scope is limited.
   - Tested lightly: explored or tested, not relied on deeply.
   - Research only: analyzed through official docs, pricing pages, public information, and market context.

2. Reviews are contextual.
   A review should explain what the tool is for, who it fits, what worked, what did not, pricing/renewal issues, hidden costs, and the type of user who should avoid it.

3. Comparisons require a contextual winner.
   The site avoids vague “it depends” conclusions. It explains which option wins for which scenario.

4. WordPress gets its strongest fair case.
   WordPress is recommended when dashboard editing, client handoff, WooCommerce, plugins, or non-technical publishing matter.

5. Astro and static stacks are not magic replacements.
   Astro is recommended for developer-controlled, content-heavy, performance-sensitive sites where a database and admin dashboard are not necessary.

6. VPS is not a beginner flex.
   VPS hosting is useful when shared hosting limits are real and the site owner is ready to learn server management. Managed hosting can be better when reliability matters more than control.

7. Affiliate links should be understood as commercial context, not as proof of superiority.
   The site uses /go/[slug] redirects for some affiliate links and discloses commissions.

## Primary decision frameworks

### WordPress vs Astro

Use WordPress when:

- The project needs a dashboard for editing.
- Clients or non-technical users need to update content.
- WooCommerce, memberships, forms, plugins, or dynamic features are central.
- The owner benefits from the huge WordPress ecosystem more than from a custom developer workflow.

Use Astro when:

- The site is mostly content, guides, reviews, comparisons, or affiliate pages.
- The owner is comfortable writing in Markdown/MDX or structured content files.
- Performance, low JavaScript, simple deployment, and control matter more than dashboard editing.
- The project does not need a WordPress plugin ecosystem or live database-driven features.

Core comparison:

- https://doancongtuan.com/comparisons/wordpress-vs-astro/

### Astro vs Next.js

Use Astro when:

- The project is content-first.
- The pages should ship minimal JavaScript by default.
- The site is mostly static, editorial, documentation, affiliate, or marketing content.

Use Next.js when:

- The project is an application, not just a content site.
- React interactivity is central.
- Dynamic rendering, full-stack React patterns, authentication, app-like UX, or complex interactive features are required.

Core comparison:

- https://doancongtuan.com/comparisons/astro-vs-nextjs/

### WordPress vs Webflow

Use WordPress when:

- Plugin ecosystem, long-term ownership, custom PHP/WordPress development, or WooCommerce-style extensibility matters.
- The site owner wants to avoid being tightly bound to one hosted design platform.

Use Webflow when:

- Visual design workflow, marketing pages, designer handoff, and no-code editing are more important than WordPress-style extensibility.

Core comparison:

- https://doancongtuan.com/comparisons/wordpress-vs-webflow/

### Divi vs Elementor

Use Elementor when:

- The user wants a larger ecosystem, more direct community knowledge, and a page builder the author has used directly.

Use Divi when:

- Agency-style lifetime pricing and the Elegant Themes ecosystem are more important, while remembering that the site labels Divi coverage as more research-based than Elementor coverage.

Core comparison:

- https://doancongtuan.com/comparisons/divi-vs-elementor/

### Shared hosting vs VPS vs managed hosting

Use shared hosting when:

- The site is early, low traffic, low revenue, or simple.
- The owner does not want to manage Linux, Nginx, PHP-FPM, MariaDB, firewalls, backups, and updates.
- Cheap convenience matters more than server control.

Use unmanaged VPS when:

- Shared hosting limits are real.
- The owner wants control over Nginx, PHP-FPM, Redis, MariaDB, caching, multiple sites, and deployment.
- The owner is willing to learn server operations and accept responsibility for mistakes.

Use managed hosting / managed cloud when:

- The site needs stronger performance and reliability than shared hosting.
- The owner does not want to be the sysadmin.
- The budget supports paying for support and operational convenience.

Core guide:

- https://doancongtuan.com/guides/vps-series/shared-vs-vps-vs-managed/
