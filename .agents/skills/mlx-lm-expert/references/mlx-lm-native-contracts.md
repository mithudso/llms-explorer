# MLX-LM native service model lifecycle and release contracts

## Overview

MLX-LM's native server implements a local OpenAI-compatible chat-completions endpoint. With stream:true, it sends prompt-progress comments, JSON delta chunks, a terminal finish reason, optional usage, and [DONE] over SSE. Error behavior depends on timing: the current code returns JSON errors before SSE starts but has no explicit SSE error frame for exceptions after the 200 stream begins. Current main detects a dead generation thread, while reports also describe a live no-delivery livelock. Downstream MLX-based servers show separate cancellation and finish-reason failures, so those reports should not be generalized to the native server.

MLX-LM architecture support is a dispatch-and-weights contract. On the built-in path, config.json selects Model and ModelArgs through model_type remappings; a custom model_file path is also available behind trust_remote_code=True. The loader constructs ModelArgs, optionally sanitizes checkpoint tensors, and checks them with strict weight loading by default. An MLX-formatted checkpoint or familiar Hugging Face model ID alone does not prove that the installed MLX-LM can build it. New integrations must match architecture semantics and checkpoint tensor layout, then compare outputs against a reference. The lower-level load_model resolver callback is not exposed by public load().

MLX-LM accepts Hugging Face repo IDs and uses the Hugging Face Hub cache to reuse downloaded model files. That cache is shared by Hub clients using the same cache configuration. Its mlx_lm.manage utility scans repo IDs and can delete matches, but defaults to the substring "mlx", so the default scan misses many source repos. Hub snapshots point to content blobs, and reference-aware deletion preserves blobs still used by other revisions. MLX conversion writes a separate mlx_model directory by default. Current Hugging Face hf cache prune also removes partial downloads left by interrupted transfers; mlx_lm.manage operates on completed revisions and does not expose that cleanup. These boundaries matter for inventory, disk usage, and deletion.

As of October 16, 2026, mlx-lm 0.32.2 was the latest PyPI release. Its published metadata requires Python 3.11 or newer, MLX 0.32.2 or newer on Darwin, and Transformers 5.7.0 or newer. Upstream main has already raised the Darwin MLX floor to 0.32.3, so its manifest must not be used to describe the 0.32.2 wheel. Python 3.10 can resolve to the older 0.31.3 release. Downstream reports also show that compatibility depends on workload and API assumptions: one custom-kernel project excluded MLX 0.32.1 after A/B testing, and another integration adapted to MLX-LM 0.32.0 changes. Reproducible deployments should lock the package pair and interpreter, then re-test before point upgrades.

## Core Concepts

### MLX-LM native HTTP request streaming and error contracts

- For POST /v1/chat/completions with stream=true, the current handler returns HTTP 200 with Content-Type: text/event-stream and Cache-Control: no-cache. It flushes each JSON chunk as a data: record ending in a blank line, then emits a final chunk carrying finish_reason, an optional usage-only chunk, and data: [DONE]. This matches WHATWG event framing and the documented Chat Completions finish and usage chunk ordering. verified-as-of: 2026-10-23[^c1-1][^c1-8][^c1-2][^c1-3]
- Current native error handling depends on when failure occurs. Request validation errors return JSON bodies with HTTP 400 or 411; an exception from response_generator.generate() before headers are sent returns an error JSON body with HTTP 404. After the server sends HTTP 200 and text/event-stream, handle_completion has a finally cleanup but no explicit SSE error-frame or [DONE] path for an exception, so a mid-stream failure can appear truncated. A historical mlx-lm 0.31.3 report also describes generation failures that surfaced no client error. verified-as-of: 2026-10-23[^c1-1][^c1-4][^c1-2]
- Before stream headers are sent, missing Content-Length returns 411; a nonnumeric length, invalid JSON, non-object JSON body, parameter validation error, or request-factory exception returns 400. An unknown POST route returns 404. An exception from generation setup also returns 404 with JSON shaped as {"error": "<message>"}, even for a streaming request; OpenAI's error guide describes NotFoundError as a missing resource, so status-based clients can misclassify a model or setup failure as a not-found error. (two sources) verified-as-of: 2026-10-23[^c1-1][^c1-9]

### MLX-LM model architecture integration and loader contracts

- In MLX-LM's built-in path, _get_classes requires config['model_type'], optionally remaps a (model_type, architectures) pair or a model-type alias, imports mlx_lm.models.<resolved-type>, and expects that module to expose Model and ModelArgs. A repository name or architecture label alone does not add an implementation to the loader. verified-as-of: 2026-10-23[^c2-1][^c2-10][^c2-2][^c2-3]
- load_model has a separate config model_file path: it imports that file and expects Model and ModelArgs. This route raises unless trust_remote_code=True, which defaults to false. A Qwen3.8 checkpoint repository demonstrates stock mlx_lm.load(..., trust_remote_code=True) using its bundled model_file for an architecture absent from the released registry. verified-as-of: 2026-10-23[^c2-1][^c2-4][^c2-5]
- load_model reads model*.safetensors, applies optional model_config overrides, builds ModelArgs.from_dict(config) and Model, calls model.sanitize(weights) when provided, then calls model.load_weights(..., strict=True) by default. A registry mapping alone therefore does not adapt checkpoint tensor names or layouts that the selected model cannot consume. verified-as-of: 2026-10-23[^c2-1][^c2-6][^c2-5][^c2-7]

### MLX-LM model management and Hugging Face cache lifecycle

- A Hugging Face model repo ID passed to an MLX-LM generation command is downloaded from the Hub when it is not already cached. Conversion writes the resulting MLX model to mlx_model by default, separate from the Hub source cache. verified-as-of: 2026-10-17[^c3-1][^c3-9]
- mlx_lm.manage calls huggingface_hub.scan_cache_dir() without a custom cache path. The Hub cache defaults to ~/.cache/huggingface/hub; HF_HUB_CACHE can set the cache directory directly and HF_HOME changes its parent. Hub clients using the same configuration can share those cached repo files. verified-as-of: 2026-10-23[^c3-2][^c3-3][^c3-9][^c3-11]
- The Hub cache stores each model repo under a models--<org>--<repo> directory. It stores commit revisions in snapshots and branch or tag pointers in refs; snapshot files point to blobs, so unchanged files can be shared across revisions without duplicate bytes. verified-as-of: 2026-10-23[^c3-3][^c3-4]
- Hugging Face revision deletion removes the selected snapshot and its refs, deletes a blob only when no remaining cached revision references it, and removes the repo cache when no revisions remain. verified-as-of: 2026-10-23[^c3-4][^c3-5]
- The default Hub cache is ~/.cache/huggingface/hub, and HF_HOME or HF_HUB_CACHE can customize its location. Hugging Face describes this as a central cache shared across Hub libraries; LocalAIScope likewise notes that other Hugging Face tools on a Mac share it. Removing a matching entry through MLX therefore changes the cache used by those tools too.[^c3-12][^c3-9]
- Hub snapshots represent repository revisions and point to content-addressed blobs, which may be shared among revisions or repositories. Hugging Face distinguishes logical per-repository sizes from physical cache size, so the per-repository SIZE ON DISK shown by mlx_lm.manage --scan is not guaranteed to equal the physical space reclaimed by deletion. verified-as-of: 2026-10-23[^c3-12][^c3-2][^c3-5]

## Tools & Frameworks

- Tentative: load_model accepts a get_model_classes callable that maps config to (Model, ModelArgs) and defaults to _get_classes. The higher-level load() signature does not expose or forward this callback, so it is a resolver hook for direct load_model callers rather than a global loader registry. verified-as-of: 2026-10-23[^c2-1] _(MLX-LM model architecture integration and loader contracts)_
- MLX-LM imports a config-declared model_file from the model directory only when trust_remote_code=True; the default is false. The merged upstream change threads this opt-in through load() and sharded_load(), and oMLX preflights the same trust decision before starting MLX-LM loading. verified-as-of: 2026-10-23[^c2-1][^c2-4][^c2-9] _(MLX-LM model architecture integration and loader contracts)_
- The current manager defaults its pattern to mlx and both scan and delete select entries when that substring occurs anywhere in repo.repo_id. A plain scan therefore omits cached repos whose IDs do not contain mlx. verified-as-of: 2026-10-23[^c3-2][^c3-9][^c3-10] _(MLX-LM model management and Hugging Face cache lifecycle)_
- mlx_lm.manage --delete applies the same pattern to repo IDs, displays the matching repos with their sizes and local paths, then asks for yes/no confirmation. On confirmation it processes every cached revision it found for each matched repo; a no or blank answer cancels deletion. verified-as-of: 2026-10-23[^c3-2][^c3-10] _(MLX-LM model management and Hugging Face cache lifecycle)_
- `mlx_lm.manage` enumerates Hub repository revisions and delegates deletion to `delete_revisions()`, rather than exposing dedicated partial-download maintenance. Current Hugging Face documentation assigns partial-download and detached-revision cleanup to `hf cache prune`; it also says `hf cache ls` flags incomplete downloads and `hf cache rm` can remove partial files when deleting an entire repository. Revision-oriented management therefore does not imply that every repository deletion leaves .incomplete files behind. verified-as-of: 2026-10-23[^c3-2][^c3-6][^c3-7][^c3-12] _(MLX-LM model management and Hugging Face cache lifecycle)_
- For --delete, a blank response means no; only y, yes, or 1 confirms. After confirmation, MLX-LM passes every revision hash for each matched repository to HFCacheInfo.delete_revisions(), so the command removes matching repo revisions rather than selecting one file. verified-as-of: 2026-10-23[^c3-2][^c3-5][^c3-12] _(MLX-LM model management and Hugging Face cache lifecycle)_

## Practical Patterns

- A vllm-mlx 0.4.0 issue reported that natural EOS streaming ended with finish_reason:null followed by [DONE], while token-cap stops emitted length; a strict OpenAI-compatible client rejected the natural-stop result. The issue was closed as fixed on 2026-08-12. This is an adjacent MLX-based implementation, not evidence that native mlx_lm.server had the same defect. (two sources) verified-as-of: 2026-08-12[^c1-5][^c1-2] _(MLX-LM native HTTP request streaming and error contracts)_
- Tentative: A downstream mlx-openai-server v1.7.0 report found that disconnecting an SSE client stopped stream consumption but did not signal its inference worker; generation continued until completion and blocked the request queue. The proposed threading.Event cancellation stopped generation within one token. This describes that wrapper's behavior, not native mlx_lm.server.[^c1-6] _(MLX-LM native HTTP request streaming and error contracts)_
- A separate mlx-openai-server issue shows a generation failure returned inside an SSE data: error object with the message 'Failed to generate text stream: There is no Stream(gpu, 1) in current thread.' That is a downstream wrapper's error envelope; current native mlx_lm.server instead writes JSON errors before streaming starts and has no explicit post-header SSE error encoder. (two sources) verified-as-of: 2026-10-23[^c1-7][^c1-1] _(MLX-LM native HTTP request streaming and error contracts)_
- When stream_options.include_usage is enabled, normal MLX-LM stream chunks omit the usage field entirely: generate_response adds usage only to non-stream responses, and the handler emits usage separately in a terminal chunk. OpenAI's documented Chat Completions contract says the other chunks include usage: null when the final usage chunk is requested, so clients that depend on this field see a compatibility difference. verified-as-of: 2026-10-23[^c1-1][^c1-2] _(MLX-LM native HTTP request streaming and error contracts)_
- Tentative: Native server POST routes are /v1/completions for text and /v1/chat/completions or /chat/completions for chat. Chat bodies require messages, while text bodies require prompt; their request factories assert those keys and the POST handler converts request-factory exceptions into a 400 JSON error. verified-as-of: 2026-10-23[^c1-11] _(MLX-LM native HTTP request streaming and error contracts)_
- Tentative: The HTTP sampling validator accepts numeric top_p in the inclusive interval [0,1]: values below zero or above one raise ValueError. The request field model chooses the model (default "default_model"), and the plural field adapters chooses an optional adapter path (default None). These names differ from the --adapter-path CLI option. verified-as-of: 2026-10-23[^c1-11] _(MLX-LM native HTTP request streaming and error contracts)_
- Tentative: Set stream=true for an SSE response. The server terminates with data: [DONE]; stream_options.include_usage adds a separate usage packet before that sentinel. Missing Content-Length returns 411; invalid JSON returns 400 with an "Invalid JSON in request body" error. verified-as-of: 2026-10-23[^c1-11] _(MLX-LM native HTTP request streaming and error contracts)_
- A model-type alias is valid only when the model graph and weight semantics match. The oMLX Xing4.0 report describes a distinct Xing4_0HyperConnection residual topology and says aliasing xing4_0 to deepseek_v3 would produce incorrect outputs; it calls for a compatible implementation and sanitizer instead. (two sources)[^c2-10][^c2-7] _(MLX-LM model architecture integration and loader contracts)_
- Tentative: _get_classes reads config.model_type and examines architectures in order, treating a string as one architecture. The first matching (model_type, architecture) entry in MODEL_ARCHITECTURE_REMAPPING wins; if none matches, MODEL_REMAPPING applies. It imports mlx_lm.models.<resolved_type> and returns that module's Model and ModelArgs. ImportError becomes ValueError("Model type <resolved_type> not supported."). verified-as-of: 2026-10-23[^c2-12] _(MLX-LM model architecture integration and loader contracts)_
- Tentative: load_model reads config.json, then calls config.update(model_config) for supplied overrides before ModelArgs.from_dict and Model construction. This is a shallow dictionary update: supplied values replace values under matching top-level keys. A model sanitize hook transforms the loaded weight dictionary before the final model.load_weights call. verified-as-of: 2026-10-23[^c2-12] _(MLX-LM model architecture integration and loader contracts)_
- Tentative: For config.quantization, the loader first honors explicit per-module entries keyed by module path. Otherwise class_predicate requires a to_quantized method and a matching <path>.scales checkpoint tensor, then infers the module quantization settings from checkpoint shapes/dtypes. A supported global_scale tensor adds that argument. This selective conversion prepares modules before weights are loaded. verified-as-of: 2026-10-23[^c2-12] _(MLX-LM model architecture integration and loader contracts)_
- Tentative: mlx_lm.manage --scan displays SIZE ON DISK from repo.size_on_disk_str and LOCAL PATH from repo.repo_path. --pattern performs a substring test against repo.repo_id. With --delete, ask_for_confirmation treats an empty response as no and prints "Deletion cancelled - no changes made."; if no repository matches, it prints "No models found matching pattern" with the pattern. verified-as-of: 2026-10-23[^c3-13] _(MLX-LM model management and Hugging Face cache lifecycle)_

An existing local model path bypasses the Hub download, so a revision string does not select a different checkpoint within that local directory. verified-as-of: 2026-10-23[^c3-14] _(MLX-LM model management and Hugging Face cache lifecycle)_

## Anti-Patterns

- The minimum architecture metadata is consumer-specific: MLX-LM requires model_type and treats architectures as optional remapping input, while Ollama issue #19128 reports that its MLX importer and runner rejected a checkpoint with model_type but no architectures[0], even though the model_type named a supported runner architecture. Services should define and validate metadata fallbacks for each backend. (two sources) verified-as-of: 2026-10-19[^c2-1][^c2-11] _(MLX-LM model architecture integration and loader contracts)_

## Troubleshooting

- Current main polls each response queue with a one-second timeout and raises RuntimeError saying the generation thread died when the generation thread is unavailable, so it no longer has the dead-thread indefinite-wait behavior described for mlx-lm 0.31.3 in issue #1493. Its health check tests thread liveness and a failure flag; it does not detect a live worker that stops delivering responses. (two sources) verified-as-of: 2026-10-23[^c1-1][^c1-4] _(MLX-LM native HTTP request streaming and error contracts)_
- Tentative: Issue #1493 does not establish a generic prompt-length or stream-only trigger: synthetic requests around the same long context, including a streaming request, passed. The later report captured a no-delivery livelock in the Gemma case; the uncaught OOM worker-exit explanation concerned a separate Qwen server. Five replay turns passed, but the reporter explicitly said that replay did not validate watchdog recovery.[^c1-4] _(MLX-LM native HTTP request streaming and error contracts)_
- If stream_options is an object without include_usage, such as {}, the handler indexes self.stream_options["include_usage"] after it has sent the finish chunk. That raises KeyError before data: [DONE]. OpenAI documents include_usage as optional, so an empty stream_options object is valid under that schema but does not complete normally in this code path. verified-as-of: 2026-10-23[^c1-1][^c1-2] _(MLX-LM native HTTP request streaming and error contracts)_
- The handler has no exception-to-SSE branch around response iteration. If generation raises after streaming has started, control skips the final finish chunk, optional usage chunk, and [DONE], although the context is stopped in finally. Clients should treat stream termination without [DONE] as incomplete; OpenAI notes that interruption may omit the final usage chunk, and WHATWG discards an event that reaches EOF without its terminating blank line. verified-as-of: 2026-10-23[^c1-1][^c1-2][^c1-8] _(MLX-LM native HTTP request streaming and error contracts)_
- Current main marks the background generation worker unavailable after an uncaught worker failure, and GET /health then returns 503; GET /v1/models remains a metadata route that returns 200. A 2026-08 report on mlx-lm 0.31.3 observed /v1/models returning 200 while a generation thread had died and streams hung, so that report describes a historical failure mode rather than the current /health response contract. (two sources) verified-as-of: 2026-10-23[^c1-1][^c1-10] _(MLX-LM native HTTP request streaming and error contracts)_
- Tentative: With strict=True, load_model raises FileNotFoundError("No safetensors found in <model_path>") if model*.safetensors matches no files. It passes strict to model.load_weights; the documented contract raises if weights do not match the model. strict=False relaxes that contract and the missing-weight-files guard. verified-as-of: 2026-10-23[^c2-12] _(MLX-LM model architecture integration and loader contracts)_
- If the configured Hub cache directory does not exist, scan_cache_dir() raises CacheNotFound. Since mlx_lm.manage --scan calls it directly, a fresh install with no cache directory can fail instead of returning an empty listing; MLX-LM issue 632 reports this behavior and its maintainer says the exception is expected. verified-as-of: 2026-10-23[^c3-2][^c3-5][^c3-8] _(MLX-LM model management and Hugging Face cache lifecycle)_
- The current implementation filters only on repo.repo_id and does not restrict repo_type. A dataset or Space whose repo ID matches the pattern can therefore appear in --scan and be selected by --delete, even though the CLI help describes models. verified-as-of: 2026-10-23[^c3-2][^c3-12] _(MLX-LM model management and Hugging Face cache lifecycle)_
- For caches using Xet shared blobs, Hugging Face warns that older cache clients can leave shared payloads behind or delete a blob still referenced by another repository. Because mlx_lm.manage delegates deletion to the installed Hugging Face delete_revisions() helper, physical cleanup behavior depends on that runtime helper; the sources do not establish one result for every installation. (two sources) verified-as-of: 2026-10-23[^c3-12][^c3-2][^c3-5] _(MLX-LM model management and Hugging Face cache lifecycle)_
- On Python 3.10, pip can select mlx-lm 0.31.3 rather than fail because 0.32.2 requires Python >=3.11; a third-party install check observed 0.31.3 as the last release accepted by Python 3.10, so verify the interpreter and installed package version after installation. (two sources) verified-as-of: 2026-10-17[^c4-2][^c4-6] _(MLX-LM version pinning and current release compatibility delta)_

## Disagreements & Open Questions

- Disagreement (MLX-LM native HTTP request streaming and error contracts): The #1493 exchange first proposed an uncaught worker exception based on a separate Qwen OOM, then later reported a live no-delivery livelock for the Gemma case and said five replay turns passed without validating recovery; it does not establish one root cause for the original hang.[^c1-4]
- Disagreement (MLX-LM native HTTP request streaming and error contracts): The August 2026 issue report says /v1/models stayed HTTP 200 after the generation worker died and that no health check distinguished the failure. Current main has a separate /health endpoint tied to generation_available() that returns 503 when the worker is unavailable; /v1/models still remains a 200 metadata route.[^c1-1][^c1-10]
- Open (MLX-LM native HTTP request streaming and error contracts): Does native mlx_lm.server stop generation promptly after a client disconnect in both its batched and sequential paths?
- Open (MLX-LM native HTTP request streaming and error contracts): What error frame or connection-close behavior should clients rely on when a generation exception occurs after SSE headers have been sent?
- Open (MLX-LM native HTTP request streaming and error contracts): No live server request was run to confirm the KeyError behavior for stream_options={}, and client behavior when [DONE] is absent varies by SDK.
- Disagreement (MLX-LM model architecture integration and loader contracts): Aditya Karnam's August 2026 explanation treats module or alias resolution as the entire model-selection path. That describes the built-in route, but current upstream load_model also has an opt-in config model_file path gated by trust_remote_code.[^c2-3][^c2-1]
- Disagreement (MLX-LM model architecture integration and loader contracts): MLX-LM issue #1578 reports that 0.31.3 lacked a public loader registry for custom bundle formats. Current main has a per-call class resolver and a model_file architecture path, but these do not establish a general bundle-format loader registry.[^c2-8][^c2-1]
- Disagreement (MLX-LM model architecture integration and loader contracts): MLX-LM treats model_type as required and architectures as optional remapping input; Ollama issue #19128 reports its MLX create and runner paths require architectures[0].
